OPS-01liaooliver/notes-deploy › main › overlays/*/kustomization.yaml

GitOps：cluster 該長什麼樣，只看 notes-deploy 的 main

唯一的真實來源是 notes-deploy 的 main。CI 只改 Git、從不連 cluster；Argo CD 在 cluster 裡把 Git 拉進來套用，這是 pull-based。

GitOps 的規則只有一條：cluster 的 desired state 寫在 Git，由一個程式持續把 cluster 拉成 Git 的樣子。在這個專案，那份 Git 是 liaooliver/notes-deploy 的 main。真正決定「跑哪個版本」的只有兩個檔：overlays/staging/kustomization.yaml 與 overlays/production/kustomization.yaml 裡的 newTag。

push-based 是 CI 在 job 最後自己跑 kubectl apply。那需要 GitHub 的 runner 連得到 k3s 的 API server（6443 port），還要把 kubeconfig 存成 GitHub secret。這個 cluster 在 Mac 上的 Multipass VM 裡，IP 是 192.168.64.x 這種私有位址，GitHub 的 runner 根本連不進來。

pull-based 反過來：Argo CD 跑在 cluster 裡面，自己往外 git fetch GitHub。VM 只要能出網就夠，沒有人需要連進來。CI 的工作到「push 一個 bump commit 進 notes-deploy」就結束，bump-staging / bump-production 裡沒有一行 kubectl。

所以「image 推上 GHCR」跟「cluster 換版」是兩件事。Argo CD 不讀 GHCR，它只看到 manifest 裡的 tag 字串變了，才把新 spec 交給 k3s，由 k3s 去 pull。

desired state
Git 裡宣告的目標狀態。這裡是 kustomize build overlays/* 算出來的 YAML。
live state
cluster 裡實際存在的物件。Argo CD 拿它跟 desired state 比對。
push-based
CI 持有 cluster 憑證，直接 kubectl apply。本專案的 runner 連不到 VM，做不到。
pull-based
cluster 內的 agent（Argo CD）主動讀 Git 並套用。只需要出網。

OPS-02GitHub › liaooliver/notes › Settings › Branches

為什麼 manifest 放在另一個 repo

notes 的 main / staging 是 classic branch protection，required check 沒有身分豁免。bot 的 bump commit 身上不會有 check，換任何 token 都推不進去，只能改寫一個不受保護的 repo。

bump commit 一定要寫進某個 Git。最初的設計是寫回 notes 的 deploy/ 目錄，但 main 與 staging 都有 classic branch protection，同時開著兩條規則。規則 A：必須透過 PR。規則 B：3 個 required status check 必須通過。

規則 A 有 bypass 名單可以放人。規則 B 在 classic 底下沒有任何身分豁免，唯一開關是 Include administrators，而 github-actions[bot] 永遠不是 admin。bot 直接 push 的 commit 沒有經過 PR，Build Application、White-box Security Scan、Validate Commit Messages 都不會出現在它身上，規則 B 必然擋下。換成 GitHub App token 或 PAT 也一樣，token 種類不會讓 check 憑空出現。

ruleset 的 bypass list 能整組豁免，但要遷移保護設定，而且「個人 repo 的 bypass 名單能不能選到 bot」沒有驗證過。最後的決定是繞開：開一個不設任何保護的 notes-deploy，CI 直接 push 它的 main。notes 的保護設定一個字都沒動。

拆開後附帶解掉兩件事。CI 寫的是別的 repo，notes 不會收到 push 事件，ci.yml 不會被自己的 bump 再觸發，所以 bump commit 不需要 skip-ci 標記，也不需要 paths-ignore。rollback 時直接 revert，不用等 PR 與 check。

classic branch protection
Settings → Branches 那一套。bypass 名單只解「必須走 PR」，解不了 required check。
required status check
指定的 check 必須在這個 commit 上成功才能進分支。沒跑過的 commit 等於沒通過。
GH006 / GH013
被擋時的錯誤碼。GH006 來自 classic，GH013 來自 ruleset，看碼就知道是哪一套。
ruleset bypass list
新版保護機制的豁免名單，整組規則一起豁免。本專案沒有採用。

OPS-03ci.yml › bump-* › Checkout config repo / Commit and Push

deploy key：CI 怎麼拿到寫 notes-deploy 的權限

GITHUB_TOKEN 只對 notes 自己有效。CI 用存成 secret 的 SSH 私鑰寫 notes-deploy；這種 push 會觸發 notes-deploy 的 Manifest Check，GITHUB_TOKEN 做出的 push 則不會觸發任何 workflow。

每個 job 自動拿到的 GITHUB_TOKEN，權限只限觸發它的 repo，也就是 notes。要寫 notes-deploy 需要另一把憑證。deploy key 是一組 SSH key：公鑰掛在 notes-deploy 的 Deploy keys 並勾 write，私鑰存成 notes 的 Actions secret DEPLOY_REPO_SSH_KEY。

runtime 時，actions/checkout 收到 ssh-key 參數，會把私鑰寫進 runner 的暫存檔、設定 core.sshCommand，改走 SSH clone。之後在 notes-deploy 目錄裡的 git push 就用這把 key。job 結束的 post step 會把 key 檔與設定刪掉。

為什麼不用 PAT：PAT 綁個人帳號，預設權限橫跨帳號下所有 repo，還會過期。deploy key 只綁 notes-deploy 一個 repo，外洩也碰不到 notes。fork 來的 PR 拿不到這個 secret，因為三個 workflow 都用 pull_request，沒有用 pull_request_target。

GitHub 有一條規則：GITHUB_TOKEN 做出的事件不會再建立新的 workflow run，用來防止 workflow 互相無限觸發。deploy key 的 push 不受這條規則限制，所以每個 bump commit 進 notes-deploy 都會觸發它自己的 Manifest Check，自動跑一次 kubectl kustomize。如果 bump 把 overlay 改壞，那裡會先紅。

deploy key
掛在單一 repo 上的 SSH 公鑰，可選唯讀或可寫。權限範圍就是那一個 repo。
GITHUB_TOKEN
每個 job 自動發的短效 token，只對觸發的 repo 有效；它產生的 push 不觸發 workflow。
ssh-key（checkout 參數）
actions/checkout 用它設定 SSH clone，並讓同一目錄後續的 git push 沿用。
non-fast-forward
push 時遠端已經有你沒有的 commit。兩個 bump 同時寫 main 就會發生。

ssh-key 參數讓 checkout 改走 SSH；depth 0 是為了之後可能要 rebase。

.github/workflows/ci.yml
          # staging 與 main 兩邊可能同時 push notes-deploy → non-fast-forward。
          # rebase 重試一次；仍失敗就讓 job 紅掉，不要靜默吞掉。
          git push origin HEAD:main \
            || { git pull --rebase origin main && git push origin HEAD:main; } \
            || { echo "::error::push 到 notes-deploy 失敗"; exit 1; }

push 失敗先 rebase 重試一次，仍失敗就讓 job 紅掉，不靜默吞掉。

notes-deploy/.github/workflows/manifest-check.yml
# PR 與 push 都跑。bump commit 是 deploy key 推的，
# 不像 GITHUB_TOKEN 那樣會被「bot push 不觸發 workflow」的規則擋掉，
# 所以每次 bump 都會自動驗一次 kustomize 算不算得出來。
on: [push, pull_request]

permissions:
  contents: read

jobs:
  manifest-check:
    name: Validate Deploy Manifests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: kustomize build
        run: |
          for overlay in overlays/*/; do
            echo "=== ${overlay} ==="
            kubectl kustomize "${overlay}" > /dev/null || exit 1
          done

註解直接寫明：deploy key 的 push 會觸發這個 workflow。

OPS-04notes-deploy › base/ + overlays/staging · overlays/production

kustomize：一份 base、兩個 overlay 目錄

base 放 5 份共用資源，overlay 只寫三種差異：namespace、兩個 image 的 newTag、Ingress host。kustomize build 把兩者合成完整 YAML，Argo CD 與 Manifest Check 跑的都是這一步。

kustomize 是 kubectl 內建的 YAML 組合工具，沒有模板語法。base/kustomization.yaml 列出 5 份資源：兩個 Deployment、兩個 Service、一個 Ingress。base 裡的 image 沒有 tag，Ingress 的 host 寫死 notes.local，也沒有 namespace。

每個 overlay 用 resources: - ../../base 引入 base，再疊三種差異。namespace: 寫進每個物件的 metadata.namespace。images: 依 name 比對所有 container 的 image 欄位，補上 newTag。patches: 是一段 JSON6902 patch，op: replace 把 /spec/rules/0/host 換掉，target 限定只作用在名為 notes 的 Ingress。

環境靠目錄分，不靠分支。兩個 Argo CD Application 都追 main，只差 path。如果用分支分環境，把 staging 驗過的設定帶到 production 就變成一次 merge，會夾帶不想帶的改動。用目錄時，production 的 bump 只改 overlays/production/kustomization.yaml 裡那兩行。

會執行 kustomize build 的有三個地方：Argo CD 的 repo-server 每次產生 manifest、notes-deploy 的 Manifest Check 每次 push、你在本機驗證。CI 的 bump job 用的是另一個子指令 kustomize edit set image，它不 build，只改寫 overlay 檔。

base
所有環境共用的資源。本專案 5 份，不帶 namespace、不帶 image tag。
overlay
引入 base 再疊差異的目錄。一個環境一個。
images[].newTag
依 image 名稱比對後補上的 tag。CI 只改這個欄位。
JSON6902 patch
用 op / path / value 精確改某個欄位；這裡用 replace 換 Ingress host。

OPS-05ci.yml › docker › Docker Metadata / bump-* › IMAGE_TAG

image tag 用 sha-40 碼 commit，staging 與 production 不是同一顆 image

tag 用完整 40 碼 commit SHA：不會碰撞、能直接對回原始碼。production 跑的是 main 的 merge commit 重新 build 的 image，跟 staging 原始碼相同，但不是同一次 build。

docker/metadata-action 的 type=sha,prefix=sha-,format=long 產生 sha- 加上 github.sha 全部 40 碼。bump job 不讀 docker job 的 outputs（matrix 的兩個分身會互相覆蓋），自己組 sha-${{ github.sha }}。兩邊都從同一個 github.sha 算，字串必然一致。web 與 api 兩顆 image 也共用這個 tag。

不用 latest：tag 字串不變，Deployment spec 就不變，Argo CD 看不到差異，不會觸發 rolling update；Git 也看不出 cluster 跑哪一版，rollback 沒有東西可以 revert。不用 7 碼短 SHA：2^28 的空間有機會碰撞，撞到時新 image 會覆寫同一個 GHCR tag，rollback 拉到的就不是當初驗過的東西。40 碼 tag 仍可以被重新 push 覆寫，真正不可變的是 digest（@sha256:…）。選 tag 是為了讓 git log 讀得出該回到哪一版。

staging 與 production 不是同一顆 image。staging → main 用 merge commit 合併，一定產生新的 commit，github.sha 不同，push main 時 docker job 用新的 SHA 再 build 一次。原始碼完全相同，產物是兩次獨立 build。嚴格來說 production 跑的不是 staging 驗過的那份二進位，只是同一份原始碼的另一次 build。

這個專案接受這個代價：build 只有 COPY 與 vite build，可重現性高，而且 main 保有獨立性，hotfix 可以不經 staging。另一種做法是 promote：bump-production 直接複製 staging overlay 的 tag，main 不 build。依賴沒鎖版、build 結果不穩定時，就該改成那樣。

github.sha
觸發這個 run 的 commit 的完整 40 碼 SHA。push main 時是那個 merge commit。
merge commit
有兩個 parent 的 commit。staging → main 的 PR 一定用它，SHA 必然是新的。
digest
registry 依內容算出的 sha256。tag 可重新指向，digest 不行。
promote
把 staging 驗過的同一個 tag 複製給 production，不重 build。本專案未採用。

OPS-06notes-deploy › argocd/notes-staging.yaml · notes-production.yaml

Argo CD Application：一次 reconcile 做了什麼

Application 告訴 Argo CD 讀哪個 repo 的哪個分支與目錄、套進哪個 namespace。預設約每 3 分鐘比對一次。Sync 看「跟 Git 一不一樣」，Health 看「跑得好不好」，兩條軸互相獨立。

Application 是 Argo CD 的 CRD。這個專案有兩個，放在 notes-deploy/argocd/，用 kubectl apply -f argocd/ 手動建一次。source 決定讀什麼：repoURL、targetRevision: main、path: overlays/staging。destination 決定套到哪：同一個 cluster 的 notes-staging。repo 是 public，Argo CD 不需要 repo 憑證。

runtime 時分兩個元件。argocd-repo-server 把 targetRevision 解析成 commit SHA，在那個 commit 的 path 跑 kustomize build，產出 desired manifest。argocd-application-controller 向 API server 讀 live 物件，逐一比對。預設約 180 秒做一次。VM 沒有公網 IP，GitHub 的 webhook 打不進來，只能靠 polling。

automated 讓 OutOfSync 時自動 apply。prune: true：Git 裡刪掉的資源，cluster 也刪。selfHeal: true：有人 kubectl edit 改了 cluster，比對發現漂移就改回 Git 的值。CreateNamespace=true：namespace 不存在時先建。production 也是 automated，人工閘只有 GitHub Environment 一道：沒人 Approve，overlay 不變，Argo CD 沒東西可以 sync。

Sync status 比的是 Git 與 live 的 spec：Synced / OutOfSync。Health status 看資源實際狀態：Healthy / Progressing / Degraded / Missing。剛 apply 完是 Synced + Progressing，新 Pod 還沒通過 readinessProbe。Git 變了還沒 apply 是 OutOfSync + Healthy，舊版仍在正常服務。image 拉不到會停在 Synced + Progressing，超過 Deployment 的 progressDeadlineSeconds（預設 600 秒）後轉成 Degraded。

targetRevision
Argo CD 追的分支或 commit。兩個 Application 都是 main，只差 path。
prune
Git 裡不存在、但 cluster 裡有 Argo CD 標記的物件，sync 時刪掉。
selfHeal
live 被手動改掉時，不等 Git 變動就自動改回 Git 的值。
Sync status
live spec 是否等於 Argo CD 目前認定的 Git revision 算出來的 spec。
Health status
依資源種類判斷的執行狀態，例如 Deployment 的新 Pod 是否都 Ready。

OPS-07Argo CD UI › Applications › notes-staging（示意，依 manifest 重畫）

Argo CD UI 的 resource tree：每個節點是誰建的

Git 裡只有 5 個物件：2 個 Deployment、2 個 Service、1 個 Ingress。樹上的 ReplicaSet、Pod、Endpoints 是 k8s controller 依這 5 個物件建出來的，Argo CD 依 ownerReferences 把它們掛上樹。

以下依 manifest 重畫，不是實機截圖。Application 底下第一層是 kustomize build 產出的 5 個物件。這一層是 Argo CD 直接 apply、也拿來跟 Git 比對 Sync status 的東西。

第二層以下不是 Argo CD apply 的。Deployment controller 看到 notes-web 的 spec，建立名字帶 pod-template-hash 的 ReplicaSet；ReplicaSet controller 再依 replicas: 1 建 Pod。Pod 通過 readinessProbe 後，它的 IP 會被寫進同名 Service 的 Endpoints / EndpointSlice。Argo CD 讀這些物件的 ownerReferences，把它們畫在所屬物件底下，狀態算進 Health，但不參與 Sync 比對。

換版時會看到兩個 ReplicaSet。image tag 改了，pod template 的 hash 跟著變，Deployment 建一個新的 ReplicaSet 擴到 1，再把舊的縮到 0。舊的不會刪，留給 kubectl rollout undo 用（預設保留 10 個）。GitOps 裡 rollback 走 Git，不用它。

Ingress 底下沒有子節點。它跟 Service 的關係是 backend.service.name 這個字串，不是 ownerReference。Deployment 與 Service 之間也一樣，只靠 label selector 對上，樹上不會把 Pod 畫在 Service 底下。

ownerReferences
子物件記錄「誰建了我」的欄位。Argo CD 用它長出樹的第二層以下。
ReplicaSet
Deployment 為每個 pod template 版本建的物件，負責維持 Pod 數量。
pod-template-hash
依 pod template 算出的 hash，出現在 ReplicaSet 與 Pod 名稱裡；image 一變就變。
Endpoints / EndpointSlice
Service 目前選到、且 Ready 的 Pod IP 清單。

OPS-08notes-deploy › git revert · Argo CD › status.sync.revision

Rollback = revert bump commit；Synced 不代表是最新 commit

退版就是在 notes-deploy revert 那個 bump commit，Argo CD 下一輪把舊 tag 套回去。判斷 Argo CD 有沒有看到最新 commit，要看 revision，不要看 Synced 兩個字。

cluster 的 desired state 就是 notes-deploy 的內容，所以退版是 Git 操作：找到那筆 chore(deploy): bump production image to sha-…，git revert 再 push。revert commit 把 overlay 的兩個 newTag 改回前一個值，web 與 api 一起回到同一版。notes-deploy 不設保護，不用開 PR 等 check。

用目前的歷史舉例：production 最近三筆 bump 是 d373a42（sha-3f51150…）、efd8792（sha-1044bc4…）、02a6026（sha-91b7f11…）。revert 02a6026 會回到 sha-1044bc4…。直接 revert 中間的 efd8792 會衝突，因為同兩行後來又被改過；要退兩版得從最新的開始依序 revert。

revert 只改 cluster，不改程式碼。下一次 promote 到 main 並 Approve，bump-production 會照常寫入新 tag，把 rollback 蓋掉；程式碼要另外走 hotfix。有人事後手動 kubectl set image 改回新版，selfHeal 也會在下一輪壓回 Git 的值。

Synced 的意思是「cluster 等於 Argo CD 目前知道的那個 commit」，不是「等於 GitHub 上最新的 commit」。polling 間隔內，UI 會是綠的 Synced，但 status.sync.revision 還停在舊 commit。要它立刻重讀，對 Application 加 argocd.argoproj.io/refresh=hard annotation，repo-server 會丟掉快取重新 fetch。

git revert
產生一個新 commit，內容是指定 commit 的反向變更。歷史不改寫。
status.sync.revision
Argo CD 目前認定的 Git commit。Synced 是相對於它，不是相對於 GitHub。

## Rollback

```bash
git revert <那個 bump commit>
git push
```

這個 repo 不設保護，不必開 PR。Argo CD 偵測到 image tag 變回舊值就會自動 rolling update 回去。

實際發生過

Phase 9 上線（UC-16、UC-17）：新增 notes-api 的結構 commit 4b60f81（2026-09-25 15:21 UTC）先被 Argo CD 讀到，而 CI 第一個替 notes-api 寫 tag 的 bump 377d045 在 15:42 UTC 才出現。中間這段 overlay 沒有 notes-api 的 images 條目，image 沒有 tag，Pod 卡在 ImagePullBackOff。kubectl rollout restart 沒用，因為 spec 沒變；讓 Argo CD 讀到 bump commit 之後才恢復。4b60f81 的 commit message 事前就寫了這個順序要求。

Mac 睡眠造成的假警報（roadmap 第 5 節）：production Pod 跑 sha-1044bc45、AGE 顯示 18h，但把 tag 換成它的 efd8792 是 15 分鐘前（2026-09-26 12:01 UTC）才推的，看起來像 cluster 比 Git 還新。VM 的 journal 在 2026-09-25T17:57:36Z 到 2026-09-26T12:04:09Z 之間一行都沒有：VM 被暫停，時鐘停住，對時後 Pod 的建立時間被蓋上舊時間戳。Git 與 cluster 其實一致。

截至 2026-09-27，notes-deploy 的歷史裡還沒有真的 revert commit。上面的 revert 流程是依 README 與 UC-19，用暫存 clone 驗證過 git revert 02a6026 會把兩個 tag 改回 sha-1044bc4…。

坑
  • kubectl rollout restart 修不了 ImagePullBackOff：spec 沒變，重建幾次都拉同一個不存在的 image。要改的是 Git，或 Argo CD 的認知。
  • 新增 Deployment 的結構 commit，要等 CI 的 bump 先把 tag 寫進 overlay 再 push；順序反了 image 沒有 tag。
  • Mac 睡醒後 VM 時鐘會往前跳，Pod AGE 多出睡眠時數。先查 journalctl 有沒有斷點，再懷疑有人繞過 Git。
  • revert 只退 cluster。下一次 promote 並 Approve 會照常寫入新 tag，程式碼的修正要另外走 hotfix。
