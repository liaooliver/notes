第 2 層 · GitHub Actions

CI 與發版

這一層從 GitHub 送出 push / pull_request 事件開始，到兩個 image 進 GHCR、bump job 把 image tag 寫進 notes-deploy、semantic-release 在 main 打 tag 為止。上游是本機 commit 與 PR 的 branch protection，下游是 Argo CD 讀 notes-deploy（GitOps 頁）。同一份 ci.yml 在 PR、push staging、push main 三種事件下跑出來的 job 完全不同，這頁就從這裡開始。

CI-01GitHub Actions › ci.yml › on / jobs.*.if

一個事件會叫醒哪些 job

on 決定 run 建不建立，各 job 的 if 決定執行或 skipped：PR 只跑 build + white-box，push 才會 build image。

GitHub 收到事件後先比對 on：push 與 pull_request 都只收 main / staging。比對成功才建立 run，ci.yml 定義的 6 個 job 全部排進 run（docker 的 matrix 展開後是 7 個），接著依 needs 的順序逐一評估各自的 if。

if 只看兩個值：github.event_name（push / pull_request）與 github.ref（refs/heads/staging / refs/heads/main）。docker 要求 push；bump-staging 要求 push + staging；bump-production 與 release 要求 push + main。條件不成立的 job 標成 skipped，不分配 runner。

這樣設計的理由：PR 階段只需要回答「這份程式碼能不能進集成分支」，不該每個 PR 都塞一份 image 進 GHCR；image 必須從 merge 後的 commit build，所以 staging 一定要聽 push（等於推翻 PR #14 的決定，代價是 build + white-box 在 merge 後重跑約 1 分鐘）。

如果 docker 少了 if，每個 PR 都會推 image，而且 PR 的 github.sha 是 GitHub 臨時產生的 merge commit，tag 對不到任何分支上的 commit。

on
workflow 的觸發條件。不符合就不建立 run，連 job 清單都沒有。
github.event_name
觸發這個 run 的事件名稱：push、pull_request、workflow_dispatch。
github.ref
觸發的 ref。push 是 refs/heads/<分支>，PR 是 refs/pull/<號>/merge。
skipped
if 為 false 的 job 仍列在 run 裡，conclusion 是 skipped，不佔 runner、不算失敗。
同一份 ci.yml 的三種 run · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟
對照程式碼
.github/workflows/ci.yml
on:
  workflow_dispatch:
  push:
    branches: [ "main", "staging" ]
  pull_request:
    branches: [ "main", "staging" ]

事件先過 on 這關；push 與 pull_request 都只收 main / staging，feature 分支的 push 連 run 都不會建立。

.github/workflows/ci.yml
  docker:
    name: Build & Push ${{ matrix.svc.name }}
    needs: white-box
    runs-on: ubuntu-latest
    if: github.event_name == 'push'

docker 只認 push。PR 事件下它與所有 needs 它的 job 一起 skipped。

.github/workflows/ci.yml
  bump-staging:
    name: Bump Staging Manifest
    needs: docker
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/staging'

bump-staging 再多要求 ref 是 staging，所以 push main 的 run 裡它是 skipped。

.github/workflows/ci.yml
  bump-production:
    name: Ops Handoff / Bump Production Manifest
    needs: docker
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    environment: production
  ...
  release:
    name: Semantic Release
    needs: bump-production
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

bump-production 與 release 用同一條條件鎖在 push main。

指令
gh run view 36241814000 --json jobs --jq '.jobs[] | "\(.conclusion)  \(.name)"'
# 依 GitHub API 對 run #84 的實際回應整理（非終端機擷取）
success  Build Application
success  White-box Security Scan
skipped  Bump Staging Manifest
skipped  Build & Push ${{ matrix.svc.name }}
skipped  Ops Handoff / Bump Production Manifest

想確認某個 run 到底跑了哪些 job 時用。注意 skipped 的 matrix job 名稱沒有展開，因為 matrix 根本沒被展開過。

實際發生過

2026-09-26 PR #44（staging → main）前後的三個 run，用 GitHub API 查 jobs 清單：

  • run #84（id 36241814000，pull_request）：Build Application 17s、White-box 37s 成功；Build & Push ${{ matrix.svc.name }}、Bump Staging、Ops Handoff、Semantic Release 四個 skipped。整個 run 約 1 分鐘。
  • run #83（id 36241721215，push staging，commit 64430d0）：build → white-box → Build & Push web / api → Bump Staging 全部成功；Ops Handoff、Semantic Release skipped。約 2 分 55 秒。
  • run #85（id 36241885140，push main，commit 91b7f11）：matrix 展開後共 7 個 job，只有 Bump Staging skipped。PR run 只有 6 筆，因為 skipped 的 docker 沒有展開。

docs/use-cases.md 的 UC-03 寫「這些 job 根本不會出現在 run 的 job 清單裡」，但 API 的回應是有列出、conclusion 為 skipped。UI 可能把它們收起來，API 看得到。

坑
  • PR 階段不 build image：Dockerfile 壞掉要等 merge 進 staging 之後的 push run 才會發現（UC-08）。
  • workflow_dispatch 手動補跑時 event_name 是 workflow_dispatch，docker 以下的 if 全部不成立，只會跑 build + white-box。目前 API 查 event=workflow_dispatch 的 run 是 0 筆，這條路還沒被實際走過。
  • commit message 出現 [skip ci] 標記時 GitHub 連 run 都不建立，required check 變成「不存在」而不是「失敗」（UC-20、PR #27 / #33）。
CI-02GitHub Actions › ci.yml › permissions / needs

needs 鏈與最小權限的 GITHUB_TOKEN

GITHUB_TOKEN 預設只讀，只有 docker 與 release 各自加寫入權；寫 notes-deploy 用的是 deploy key。

GITHUB_TOKEN 是 runner 啟動每個 job 時自動產生的短期 token，job 結束就失效，只對當前 repo（liaooliver/notes）有效。它能做什麼由 permissions 決定。repo 設定的 default_workflow_permissions 是 read（gitops-roadmap 4-a 盤點），ci.yml 頂層再明寫 contents: read。

job 層的 permissions 會整組取代頂層設定，不是疊加。所以 docker 要重寫一次 contents: read 再加 packages: write（push GHCR 用）；release 寫 contents: write（打 tag、建 Release 用），沒列到的 scope 一律沒有權限。

needs 把 job 串成一條鏈：build → white-box → docker → bump-* → release。上游失敗，下游直接 skipped；上游被取消，下游標成 cancelled。這條鏈就是「測過、掃過的才能變成 image，image 推上去才能改 manifest，manifest 改了才能發版」。

bump 兩個 job 要寫的是另一個 repo，GITHUB_TOKEN 做不到，所以用 DEPLOY_REPO_SSH_KEY 這把只綁 notes-deploy 的 deploy key。這也是 bump-staging 刻意不要 contents: write 的原因：它根本不寫 notes。

GITHUB_TOKEN
每個 job 自動拿到的短期 token，只對本 repo 有效；它產生的 push 不會再觸發 workflow。
permissions
限定 GITHUB_TOKEN 的 scope。job 層設定會整組取代頂層，未列出的 scope 為 none。
needs
job 之間的先後與依賴；上游失敗，下游 skipped。
deploy key
綁單一 repo 的 SSH 金鑰，勾 allow-write 才能 push。
job 依賴與權限 · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟
對照程式碼
.github/workflows/ci.yml
# 預設最小權限；只有 release job 需要寫入權限，於該 job 另外覆寫。
permissions:
  contents: read

頂層只給讀。沒有自己寫 permissions 的 job（build、white-box、兩個 bump）全部繼承這一行。

.github/workflows/ci.yml
  white-box:
    name: White-box Security Scan
    needs: build
  ...
  docker:
    name: Build & Push ${{ matrix.svc.name }}
    needs: white-box
    runs-on: ubuntu-latest
    if: github.event_name == 'push'
    permissions:
      contents: read
      packages: write

needs 串起先後；docker 的 permissions 要重寫 contents: read，因為 job 層會整組取代頂層。

.github/workflows/ci.yml
  bump-staging:
    name: Bump Staging Manifest
    needs: docker
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/staging'
    # 注意這裡沒有 contents: write —— 這個 job 不寫 notes，
    # 寫 notes-deploy 的權限來自 DEPLOY_REPO_SSH_KEY，跟 GITHUB_TOKEN 無關。

bump-staging 刻意沒有 contents: write，寫 notes-deploy 的權限來自 ssh-key。

.github/workflows/ci.yml
  release:
    name: Semantic Release
    needs: bump-production
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    permissions:
      contents: write
  ...
      - name: Run semantic-release
        run: npx semantic-release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

release 只要 contents: write；token 經由環境變數交給 semantic-release。

實際發生過

run #67（id 36157804851，PR #35 promote 到 main）的 Semantic Release log：

  • Created tag notes-v1.5.0、Published GitHub release 成功，因為 contents: write 夠用。
  • 接著 @semantic-release/github 的 success 步驟連續三行 ✘ Not allowed to add a comment to the issue/PR #35.（#33、#34 同樣），因為 release job 只有 contents，沒有 issues / pull-requests 的寫入權。job 仍是綠的。

另一個 needs 鏈的例子：run #65（id 36157539053）的 api 分身被取消後，Bump Staging、Ops Handoff、Semantic Release 三個下游 job 全部標成 cancelled。

坑
  • job 層 permissions 不是在頂層上「加」權限，而是整組換掉。想給 release 留言權限，要在 release 那一段補 issues: write / pull-requests: write，不是改頂層。
  • GITHUB_TOKEN 產生的 push 不會觸發新的 workflow run。這是防無限迴圈的保險，也代表用它推的 commit 不會有任何 check（gitops-roadmap 4-a）。
  • deploy key 少勾 allow-write 時 clone 會成功、push 才失敗，錯誤訊息只寫 access denied。
CI-03GitHub Actions › ci.yml › build / white-box

build → white-box：進 image 的就是測過的那份

build 測完把 dist 存成 artifact，white-box 另開 runner 掃描，web 分身下載同一份 dist 進 image。

每個 job 都是一台全新的 runner，彼此不共用檔案系統。build 在 runner 上跑 npm ci：根目錄的 package-lock.json 一次裝好 frontend 與 api 兩個 workspace；npm test 轉派給兩邊各跑 vitest run；npm run build 只跑 frontend 的 vite build，產出 frontend/dist/。

build 最後用 upload-artifact 把 dist 存成 dist-files。docker 的 web 分身不重 build，而是 download-artifact 拿回同一份 dist，再由 Dockerfile 的 COPY dist/ 放進 nginx。這保證 image 裡的靜態檔就是剛才通過測試的那一份。api 沒有 build 步驟，原始碼直接進 image，所以 api 分身跳過下載。

white-box 用 needs: build 排在後面，自己重新 checkout。Semgrep 用 p/ci 規則集做 SAST；Trivy scan-type: fs 讀 repo 裡的 lock file 找套件 CVE，severity: CRITICAL,HIGH 加 exit-code: 1 表示掃到就讓 job 失敗，ignore-unfixed 只算已有修補版的漏洞。

Build Application 與 White-box Security Scan 是 branch protection 的 required checks（外加 commitlint 的 Validate Commit Messages），任一個紅，PR 的 Merge 按鈕就是灰的。

npm workspaces
一個根 package.json 管多個子專案；lock file 只有根目錄一份。
artifact
job 之間傳檔案的機制；這裡 retention-days: 1，一天後過期。
SAST
不執行程式、直接讀原始碼找危險寫法；這裡由 Semgrep 負責。
exit-code
Trivy 掃到符合條件的漏洞時用這個結束碼離開，非 0 就讓 step 失敗。
檔案怎麼從 build 走到 image · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟
對照程式碼
package.json
  "workspaces": ["frontend", "api"],
  "scripts": {
    "test": "npm run test --workspaces --if-present",
    "build": "npm run build --workspace frontend",

test 轉派給所有 workspace；build 只轉派給 frontend。

.github/workflows/ci.yml
      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: 'npm'

      - name: Install Dependencies
        run: npm ci
      - name: Run Tests
        run: npm test
      - name: Run Build
        run: npm run build

      - name: Upload Build Artifact
        uses: actions/upload-artifact@v7
        with:
          name: dist-files
          path: frontend/dist/
          retention-days: 1

build job 的五個動作；最後一步把 dist 交給 artifact 儲存，保留 1 天。

.github/workflows/ci.yml
      - name: Run Semgrep SAST
        run: |
          docker run --rm -v "${{ github.workspace }}:/src" returntocorp/semgrep semgrep --config=p/ci /src

      - name: Run Trivy Vulnerability Scanner
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'
          ignore-unfixed: true
          format: 'table'
          severity: 'CRITICAL,HIGH'
          exit-code: '1' # 抓到高風險 CVE 立即熔斷 Pipeline

Semgrep 直接用 docker run；Trivy fs 掃到 CRITICAL/HIGH 就 exit 1。

.github/workflows/ci.yml
      # 只有前端需要：用 build job 的產物，不重新 build
      # ——確保「進 image 的東西」=「通過測試的東西」。
      - name: Download Build Artifact
        if: matrix.svc.name == 'web'
        uses: actions/download-artifact@v8
        with:
          name: dist-files
          path: dist

只有 web 分身下載；api 沒有 build 產物。

Dockerfile
FROM nginx:1.30-alpine
RUN apk upgrade --no-cache libexpat
COPY frontend/nginx.conf /etc/nginx/conf.d/default.conf
# 把 build 好的靜態檔放到 nginx 預設 docroot
COPY dist/ /usr/share/nginx/html/

image 只 COPY 已經 build 好的 dist，裡面沒有任何 npm 指令。

實際發生過
  • run #83（push staging）：Build Application 17s，其中 npm ci 7s、npm test 3s、npm run build 不到 1s；White-box 23s，Semgrep 14s、Trivy fs 5s。
  • run #85（push main）：White-box 40s，Semgrep 19s、Trivy fs 12s。
  • run #39（2026-09-18，release-automation.md 第六階段）：dist-files artifact 863 bytes，對得上當時真正的 index.html + app.js，用來確認 build 產物不是 placeholder。
  • PR #8 之前每個 PR 的 Build Application 都在 npm ci 失敗：EUSAGE ... lock file's conventional-commits-filter@5.0.0 does not satisfy conventional-commits-filter@6.0.1，因為 package-lock.json 沒跟 package.json 一起 commit（UC-05）。
坑
  • artifact 只保留 1 天。超過一天才 re-run docker job，Download Build Artifact 會找不到 dist-files（依 retention-days 推論，未實際發生過）。
  • Trivy fs 只看得到 lock file，看不到 nginx:1.30-alpine / node:22-alpine 裡的系統套件；那一層由 docker job 的 Trivy image 補掃（ci-04）。
  • required check 認的是 job 的 name（Build Application、White-box Security Scan）。改 name 等於讓 branch protection 等一個永遠不會出現的 check。
CI-04GitHub Actions › ci.yml › docker（matrix: web / api）

docker matrix：兩個分身、兩種架構、各自的 cache

matrix 開出 web / api 兩個分身，各自 build amd64 + arm64、推 sha-<40 碼> tag，再用 Trivy 掃 image。

strategy.matrix.svc 有兩筆，Actions 在排程時把 docker 展開成「Build & Push web」與「Build & Push api」兩個獨立 job，各拿一台 runner 同時跑。兩者只差 Dockerfile 路徑與 image 名稱，步驟共用。下游的 needs: docker 要等兩個分身都成功才放行。

runner 是 amd64，Mac 上 Multipass VM 裡的 k3s 是 arm64。setup-qemu-action 讓 amd64 機器能執行 arm64 指令，setup-buildx-action 提供能一次輸出多架構的 builder，platforms: linux/amd64,linux/arm64 讓 GHCR 上的一個 tag 變成 manifest list，底下掛兩份 image。k3s 拉取時 containerd 回報自己是 arm64，registry 就給 arm64 那份。

metadata-action 依兩條規則產生 tag：type=sha,format=long 產生 sha-<40 碼 commit>（manifest 只用這個），type=ref,event=branch 產生分支名（staging / main，給人工 pull 用）。build 的 layer cache 存在 GitHub Actions cache，scope 用分身名稱分開。

push 之後再用 Trivy scan-type: image 掃剛推上去的那顆，補上 fs 掃描看不到的 base image 系統套件。這一步不需要另外登入：前面的 Login to GHCR 已經把憑證寫進 runner 的 docker config。matrix job 刻意不設 outputs，兩個分身會寫同一組 outputs 互相覆蓋；下游自己組 sha-${{ github.sha }}。

matrix
同一個 job 定義依變數展開成多個 job 平行跑；fail-fast 預設 true。
QEMU / buildx
QEMU 模擬別的 CPU 架構；buildx 是能一次輸出多架構的 builder。
manifest list
一個 tag 底下掛多份依 platform 區分的 image，拉取端自動挑對的。
GHA cache scope
type=gha 快取的命名空間；不分開時兩個分身會寫同一塊。
兩個分身同時跑 · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟
對照程式碼
.github/workflows/ci.yml
    # 這裡刻意沒有 outputs：matrix 開出來的兩個分身共用同一組 outputs，會互相覆蓋只留最後一個。
    # 下游要 tag 自己組 sha-<commit> 就好，兩個 image 本來就來自同一個 commit。
    strategy:
      matrix:
        svc:
          - { name: web, image: notes,     dockerfile: Dockerfile }
          - { name: api, image: notes-api, dockerfile: api/Dockerfile }

matrix 兩筆就是兩個分身；刻意沒有 outputs 的理由寫在註解裡。

.github/workflows/ci.yml
      # QEMU：讓 amd64 的 runner 能產出 arm64 的 layer。

少了 QEMU + buildx，產出只有 amd64，arm64 的 k3s 拉不動。

.github/workflows/ci.yml
      - name: Docker Metadata (tags & labels)
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository_owner }}/${{ matrix.svc.image }}
          tags: |
            type=sha,prefix=sha-,format=long
            type=ref,event=branch

兩條規則各產生一個 tag：sha-<40 碼> 與分支名。

.github/workflows/ci.yml
        with:
          context: .
          file: ${{ matrix.svc.dockerfile }}
          platforms: linux/amd64,linux/arm64   # ← 關鍵的一行
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          # scope 一定要分開。不指定的話 web 與 api 兩個分身會同時寫同一塊

          cache-from: type=gha,scope=${{ matrix.svc.name }}
          cache-to: type=gha,mode=max,scope=${{ matrix.svc.name }}

platforms 決定兩種架構；scope 用分身名稱分開 cache（liaooliver/notes#38）。

.github/workflows/ci.yml
      - name: Scan Pushed Image with Trivy
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'image'
          image-ref: ghcr.io/${{ github.repository_owner }}/${{ matrix.svc.image }}:sha-${{ github.sha }}
          format: 'table'
          severity: 'CRITICAL,HIGH'
          ignore-unfixed: true
          exit-code: '1'
          cache: 'true'

掃的 tag 與 bump 寫進 manifest 的 tag 完全相同（liaooliver/notes#39）。

CI-05GitHub Actions › ci.yml › concurrency / Abort if branch has moved on

concurrency 與「分支已前進」的競態保護

同分支一次只跑一個 run、不取消舊的；bump 前再比對分支 HEAD，擋住舊 run 把舊 tag 寫回去。

concurrency.group: deploy-${{ github.ref }} 讓 GitHub 以 ref 為單位排隊：refs/heads/staging 一組、refs/heads/main 一組，PR 各自是 refs/pull/<號>/merge，互不影響。群組裡有 run 在跑時，新 run 進入 pending，連一個 job 都不建立。同一群組只保留一個 pending，更新的 pending 進來時，較舊的 pending 會被取消。

cancel-in-progress: false 是刻意的：bump-production 可能正停在人工審核，如果被新 run 取消，那個 Approve 就白等了。代價是一個卡住的 run 會擋住後面所有同分支的 run。

concurrency 只保證「不同時跑」，不保證「舊的不會晚寫」。IMAGE_TAG 取自觸發當下的 github.sha，而 bump 真正執行時分支可能已經前進。所以兩個 bump job 在動手前先 git fetch，比對 origin/<分支> 與 GITHUB_SHA，不相等就 exit 1 放棄，讓比較新的 run 去寫。

如果沒有這道檢查：10:00 push A、10:02 push B，run B 先完成把 manifest 寫成 sha-BBB，run A 之後才跑到 bump，又把 manifest 改回 sha-AAA，叢集部署回舊版（gitops-roadmap Phase 4）。

concurrency group
同名群組同時只有一個 run 在跑；其餘最多一個 pending，更舊的 pending 被取消。
cancel-in-progress
true 時新 run 會取消正在跑的舊 run；ci.yml 設 false，llm-pr-assist.yml 設 true。
GITHUB_SHA
觸發這個 run 的 commit，整個 run 期間固定不變。

CI-06GitHub Actions › ci.yml › bump-staging / bump-production

bump job：把 image tag 寫進 notes-deploy

用 deploy key checkout notes-deploy，kustomize 改兩行 newTag 後 commit、push，撞車就 rebase 重試一次。

bump job 的 runner 上同時有兩個 repo。第一次 checkout 是 notes 本身，fetch-depth: 1，只為了做 ci-05 的 Abort 檢查。第二次 checkout 帶 repository: liaooliver/notes-deploy 與 ssh-key，放在 notes-deploy/ 子目錄，fetch-depth: 0 抓完整歷史，因為後面 push 撞車時要 git pull --rebase，shallow clone 做 rebase 會出事。

接著在 overlays/staging（或 overlays/production）跑兩次 kustomize edit set image，web 與 api 各一次，tag 都是 sha-${{ github.sha }}。這個指令只改 kustomization.yaml 裡 images: 的 newTag，不動其他內容。沒有變化就 exit 0，有變化才以 github-actions[bot] 身分 commit。

push 到 notes-deploy 的 main。staging 與 main 兩條 run 可能同時寫這個分支，後到的會收到 non-fast-forward，這時 pull --rebase 再推一次；還是失敗就印 ::error:: 並讓 job 紅掉，不靜默吞掉。

bump commit 落在另一個 repo，notes 的 ci.yml 看不到它，所以不需要 [skip ci] 標記，也不會觸發迴圈。push 之後 notes-deploy 自己的 manifest-check 會跑，Argo CD 在下一次 polling 讀到新 commit，這些屬於 GitOps 頁。

non-fast-forward
遠端分支已有本機沒有的 commit，直接 push 會被拒絕。

CI-07GitHub Actions › ci.yml › bump-production › environment

environment: production 的人工審核閘

environment: production 讓 bump-production 在拿到 runner 前停在 Waiting，等人 Approve、Reject 或逾時。

docker 兩個分身成功後，bump-production 符合 needs，但它宣告了 environment: production。GitHub 先檢查這個 environment 的保護規則：Deployment branches 只允許 main，並且有 required reviewers。規則未滿足時，job 已建立但不分配 runner，run 狀態變成 Waiting，審核人收到「requested your review to deploy to production」通知。

這段等待不佔 runner。Approve 之後 GitHub 才分配 runner，job 從第一個 step（checkout）開始跑，所以 checkout 拿到的是「按下 Approve 當下」的 main。這正是 ci-05 的 Abort 檢查在 production 特別重要的原因：Approve 可能等了好幾個小時。

Reject 會讓 bump-production 失敗，release 因 needs 連帶 skipped，run 紅燈。沒人處理時，run 停在 Waiting，最多 30 天後自動失敗（UC-11）。兩種情況下 image 都已經在 GHCR 上，但 notes-deploy 的 production overlay 沒被改，叢集維持舊版，也沒有新 tag。

這道閘把「合併進 main」和「部署到 production」切成兩個決定。Deployment branches 限定 main 是第二層保險：就算哪天 if 被改壞，其他分支的 run 也進不了這個 environment。

environment
GitHub 的部署目標設定，可掛審核人、分支限制、secrets；job 用 environment: 名稱 綁定。
required reviewers
指定的人 Approve 之前，綁這個 environment 的 job 不會開始。
Waiting
run 在等 environment 審核時的狀態；job 已建立但沒有 runner。

CI-08GitHub Actions › ci.yml › release › npx semantic-release（.releaserc.json）

semantic-release：只打 tag、不寫回 main

semantic-release 依上次 tag 之後的 feat / fix 算版號，只打 tag、發 Release，不 commit 回 main。

release job 用 fetch-depth: 0 checkout，因為 semantic-release 要從 git 歷史找 tag。npx semantic-release 依 .releaserc.json 依序執行：先驗 GITHUB_TOKEN，找到符合 tagFormat: notes-v${version} 的最新 tag，列出之後的 commit，交給 commit-analyzer 逐一判斷。

判斷只看 Conventional Commits 的 type：feat → minor、fix → patch、BREAKING CHANGE → major，其他 type（chore、docs、ci、release）與 GitHub 的 Merge pull request 都不觸發。取最高的一級算出下一版，release-notes-generator 產生說明，@semantic-release/github 打 tag 並建立 GitHub Release。全部都不觸發時印 no release，job 仍是綠的。

2026-09-18 run #32 時還有 @semantic-release/git，它要把 CHANGELOG 與 package.json 的版本 commit 回 main，被 branch protection 以 GH006 擋下（必須走 PR、3 個 required checks）。GITHUB_TOKEN 產生的 commit 本來就不會觸發 check，第二條規則在 classic protection 底下無解。最後拿掉 git / changelog / npm 三個 plugin，只打 tag。tag 不受分支保護管，也不會觸發 ci.yml（它只聽 branch push）。

所以 package.json 的 version 停在 1.2.1、CHANGELOG.md 停在 1.2.1 是預期行為。版本的唯一來源是 notes-v* tag 與 GitHub Releases。

tagFormat

GH006
classic branch protection 拒絕 push 的錯誤碼（ruleset 是 GH013）。

LLM PR Assist：三個平行 job 與 Gemini fallback

三個 job 平行呼叫 Gemini 再貼 PR 留言；失敗就貼 fallback，新 push 取消舊 run，不擋 merge。

llm-pr-assist.yml 只聽 pull_request 的 opened / synchronize / reopened，沒有限制目標分支。三個 job 沒有 needs，排程時同時拿三台 runner：commit-message-suggestion 用 gh pr view --json commits 收 commit 標題；pr-diff-summary 與 code-review-comment 用 git diff origin/<base>...HEAD（排除 package-lock.json）並截前 20000 bytes。

三個 job 都呼叫 node scripts/llm/call-gemini.mjs --prompt-file prompt.txt，腳本直接用 Node 內建的 fetch 打 generateContent（預設 gemini-3.6-flash）。收到 429 或 503 時等 5 秒重試一次，還是失敗就依狀態碼印 fallback 文字；其他錯誤在 main() 統一印 GENERIC_FALLBACK。腳本永遠 exit 0，stdout 寫進 gemini-output.txt，再用 gh pr comment 貼出。

呼叫與留言兩個 step 都有 continue-on-error: true，三個 job 也不在 required checks 裡，Gemini 掛了不會擋 merge。workflow 層需要 pull-requests: write 才能留言。

concurrency 以 PR 號分組、cancel-in-progress: true，跟 ci.yml 相反。理由：LLM 的建議只對最新 commit 有意義，舊 run 繼續跑只是浪費免費額度，被取消也沒有不可逆的後果；ci.yml 的舊 run 可能正在等 Approve，取消就白按了。

continue-on-error
step 失敗時 job 仍算成功，後面的 step 照跑。
fallback
外部服務失敗時改輸出的替代文字，讓流程不中斷。
TRANSIENT_STATUSES
call-gemini.mjs 認定可以重試的狀態碼：429（額度）與 503（過載）。
一個 job 的 Gemini 呼叫 · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟

async function callGeminiWithRetry(prompt) {
  try {
    return await callGemini(prompt);
  } catch (error) {
    if (TRANSIENT_STATUSES.has(error.status)) {
      console.error(`Gemini transient error (${error.status}), retrying once after backoff...`);
      await sleep(5000);
      try {
        return await callGemini(prompt);
      } catch (retryError) {
        if (TRANSIENT_STATUSES.has(retryError.status)) {
          console.error(retryError.message);
          return fallbackForStatus(retryError.status);
        }
        throw retryError;
      }
    }
    throw error;

429 / 503 重試一次，仍失敗回 fallback；其他錯誤往外丟。
