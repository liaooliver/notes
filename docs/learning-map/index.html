一個 commit 怎麼變成 k3s 裡的 Pod

這張圖是整個專案在 runtime 的樣子：左上是你的 Mac 和 GitHub，中間是 GitHub Actions，下半部是 Multipass VM 裡的 k3s。 選一個情境逐步播放，看事件怎麼流；或直接點任何方塊，下方會列出它對應的知識點。

點圖上的方塊或虛線框，這裡列出對應的知識點。

實線箭頭：主動呼叫或推送（push、API 請求）
虛線箭頭：輪詢或拉取（Argo CD polling、kubelet pull）、事後產物

閱讀路線

由上往下就是一個 commit 走過的順序。每個知識點頂端都有一張縮小的總圖，標出它在哪裡。

第 1 層 · 本機與 GitHub

Git 流程規則

這一層管的是 commit 從你的 Mac 出發，一路到 PR 被 merge 為止：本機 hook 先擋訊息格式，GitHub 再用 branch protection 擋 merge。merge 之後的 push 事件交給 GitHub Actions（CI 頁），這裡只講「什麼時候會叫醒它、什麼時候叫不醒」。

  1. GIT-01分支模型：feature/* → staging → main，每一步叫醒什麼功能分支 push 什麼都不跑；PR 跑三個 required check；merge 後的 push 才會 build image。只有 push 到 main 會出現人工 Approve 與發版。
  2. GIT-02commit-msg hook：husky 怎麼掛上 git，commitlint 何時執行npm install 觸發 prepare 跑 husky，husky 把 git 的 hooksPath 指到 .husky/_。之後每次 git commit，git 先跑 commitlint，exit 非 0 就不寫入 commit。
  3. GIT-03CI 的 commitlint：PR 檢的跟 merge 後進歷史的，不是同一顆 commitPR 階段 lint 的是分支上的 commit；squash merge 時在網頁上寫的標題是新 commit，只在 merge 後的 push 才被 lint。它一旦進了受保護分支就改不掉，只能改規則。
  4. GIT-04Branch protection：三個 check 名稱、不要求 approve、直接 push 被拒main 與 staging 都要求走 PR，且三個 check 必須 success。GitHub 用 job 的 name 字串比對 required 清單，不看 workflow 檔名。approve 數設 0，因為單人 repo 自己不能 approve 自己。
  5. GIT-05promote staging → main 一定要 merge commit：squash 會切斷祖先squash 產生的 commit 只有一個 parent（舊 main），git 不知道內容來自 staging。下一次 promote 要重放 22 顆 commit、每個檔案都衝突。修法是 -s ours 把 main 記成 staging 的 parent，而且修的那個 PR 本身也不能 squash。
  6. GIT-06skip-ci 標記：訊息裡出現那個字串，run 根本不會被建立GitHub 在建立 run 之前先看 head commit 訊息，任何一行出現 skip-ci 標記就不建立。不是失敗，是不存在：沒有東西能 re-run，PR 上的 required check 也永遠不會出現。
  7. GIT-07Conventional Commits 的 type 決定下一個版號發版時 commit-analyzer 逐顆讀 main 上次 tag 之後的 commit header：feat 升 minor，fix / perf 升 patch，BREAKING CHANGE 升 major，其餘不發版。取所有 commit 中最高的那一級。
第 2 層 · GitHub Actions

CI 與發版

這一層從 GitHub 送出 push / pull_request 事件開始，到兩個 image 進 GHCR、bump job 把 image tag 寫進 notes-deploy、semantic-release 在 main 打 tag 為止。上游是本機 commit 與 PR 的 branch protection，下游是 Argo CD 讀 notes-deploy（GitOps 頁）。同一份 ci.yml 在 PR、push staging、push main 三種事件下跑出來的 job 完全不同，這頁就從這裡開始。

  1. CI-01一個事件會叫醒哪些 jobon 決定 run 建不建立，各 job 的 if 決定執行或 skipped：PR 只跑 build + white-box，push 才會 build image。
  2. CI-02needs 鏈與最小權限的 GITHUB_TOKENGITHUB_TOKEN 預設只讀，只有 docker 與 release 各自加寫入權；寫 notes-deploy 用的是 deploy key。
  3. CI-03build → white-box：進 image 的就是測過的那份build 測完把 dist 存成 artifact，white-box 另開 runner 掃描，web 分身下載同一份 dist 進 image。
  4. CI-04docker matrix：兩個分身、兩種架構、各自的 cachematrix 開出 web / api 兩個分身，各自 build amd64 + arm64、推 sha-<40 碼> tag，再用 Trivy 掃 image。
  5. CI-05concurrency 與「分支已前進」的競態保護同分支一次只跑一個 run、不取消舊的；bump 前再比對分支 HEAD，擋住舊 run 把舊 tag 寫回去。
  6. CI-06bump job：把 image tag 寫進 notes-deploy用 deploy key checkout notes-deploy，kustomize 改兩行 newTag 後 commit、push，撞車就 rebase 重試一次。
  7. CI-07environment: production 的人工審核閘environment: production 讓 bump-production 在拿到 runner 前停在 Waiting，等人 Approve、Reject 或逾時。
  8. CI-08semantic-release：只打 tag、不寫回 mainsemantic-release 依上次 tag 之後的 feat / fix 算版號，只打 tag、發 Release，不 commit 回 main。
  9. CI-09LLM PR Assist：三個平行 job 與 Gemini fallback三個 job 平行呼叫 Gemini 再貼 PR 留言；失敗就貼 fallback，新 push 取消舊 run，不擋 merge。
第 3 層 · GHCR → notes-deploy → Argo CD

GitOps 鏈路

這一層從 image 已經躺在 GHCR 開始。CI 把新的 tag 寫進 notes-deploy 這個 repo，Argo CD 在 k3s 裡讀 Git、算出差異、套進 notes-staging / notes-production。上游是 CI 與發版；Deployment、Service、Ingress 本身怎麼運作，交給 k8s runtime 那一頁。

  1. OPS-01GitOps：cluster 該長什麼樣，只看 notes-deploy 的 main唯一的真實來源是 notes-deploy 的 main。CI 只改 Git、從不連 cluster；Argo CD 在 cluster 裡把 Git 拉進來套用，這是 pull-based。
  2. OPS-02為什麼 manifest 放在另一個 reponotes 的 main / staging 是 classic branch protection，required check 沒有身分豁免。bot 的 bump commit 身上不會有 check，換任何 token 都推不進去，只能改寫一個不受保護的 repo。
  3. OPS-03deploy key：CI 怎麼拿到寫 notes-deploy 的權限GITHUB_TOKEN 只對 notes 自己有效。CI 用存成 secret 的 SSH 私鑰寫 notes-deploy；這種 push 會觸發 notes-deploy 的 Manifest Check，GITHUB_TOKEN 做出的 push 則不會觸發任何 workflow。
  4. OPS-04kustomize：一份 base、兩個 overlay 目錄base 放 5 份共用資源，overlay 只寫三種差異：namespace、兩個 image 的 newTag、Ingress host。kustomize build 把兩者合成完整 YAML，Argo CD 與 Manifest Check 跑的都是這一步。
  5. OPS-05image tag 用 sha-40 碼 commit，staging 與 production 不是同一顆 imagetag 用完整 40 碼 commit SHA：不會碰撞、能直接對回原始碼。production 跑的是 main 的 merge commit 重新 build 的 image，跟 staging 原始碼相同，但不是同一次 build。
  6. OPS-06Argo CD Application：一次 reconcile 做了什麼Application 告訴 Argo CD 讀哪個 repo 的哪個分支與目錄、套進哪個 namespace。預設約每 3 分鐘比對一次。Sync 看「跟 Git 一不一樣」，Health 看「跑得好不好」，兩條軸互相獨立。
  7. OPS-07Argo CD UI 的 resource tree：每個節點是誰建的Git 裡只有 5 個物件：2 個 Deployment、2 個 Service、1 個 Ingress。樹上的 ReplicaSet、Pod、Endpoints 是 k8s controller 依這 5 個物件建出來的，Argo CD 依 ownerReferences 把它們掛上樹。
  8. OPS-08Rollback = revert bump commit；Synced 不代表是最新 commit退版就是在 notes-deploy revert 那個 bump commit，Argo CD 下一輪把舊 tag 套回去。判斷 Argo CD 有沒有看到最新 commit，要看 revision，不要看 Synced 兩個字。
第 4 層 · Multipass VM 裡的 k3s

k8s runtime

這一層從「manifest 已經被 Argo CD apply 進 cluster」開始。接下來是 k3s 自己的事：controller 把 Deployment 變成 Pod、Service 靠 label 找到 Pod、Traefik 把瀏覽器的 request 送到對的容器。每個知識點都拆成「誰呼叫誰、依序發生什麼」。

  1. K8S-01環境全貌：Mac 裡的 VM 裡的單節點 k3s整個 cluster 是 Mac 上一台 6 GB 的 arm64 VM；control-plane 與 worker 是同一台，Traefik、ServiceLB、CoreDNS 都是 k3s 內建。
  2. K8S-02Namespace：一個 cluster 放兩個環境物件的唯一鍵是 kind + namespace + name，所以兩個 notes-web 不衝突；namespace 隔開的是名稱，不是網路也不是資源。
  3. K8S-03Deployment → ReplicaSet → Pod：image tag 變了之後tag 一變就產生新的 ReplicaSet；replicas 1 的預設策略是先多開一個新 Pod，readinessProbe 通過之後才殺舊 Pod。
  4. K8S-04Service 與 label selector：流量怎麼找到 PodService 用 selector 挑 Pod，endpoints controller 把「符合 label 且 Ready」的 Pod IP 列成清單；少一個 label 就會選錯 Pod，而且不會報錯。
  5. K8S-05一個 request 的完整路徑：瀏覽器到 Pod/etc/hosts 把網址指到 VM，ServiceLB 把 80 port 交給 Traefik，Traefik 依 host 與最長前綴挑 Service，再直接連 Pod IP。
  6. K8S-06容器裡面：nginx 與 Express 各自在做什麼web image 是 nginx 加上 build 好的 Vue 靜態檔，靠 try_files 撐 SPA；api image 是單層 node:22-alpine 跑 Express，資料只在記憶體。
  7. K8S-07image pull：kubelet 怎麼從 GHCR 拿到 arm64 那一份public package 用匿名 token 就拉得到，不需要 imagePullSecrets；tag 背後是 image index，containerd 自己挑 linux/arm64。tag 不存在時 restart 沒有用。
  8. K8S-08resources：requests 給 scheduler 看，limits 給 kernel 執行scheduler 只拿 requests 算放不放得下；limits 寫進 cgroup，CPU 超過會被限速，記憶體超過會被 OOMKilled。
  9. K8S-09Traefik 回 no available server：從外往內排錯no available server 代表路由有對到，但那個 Service 的 endpoints 是空的：不是 selector 對不到 Pod，就是 Pod 還沒 Ready。
工具箱 · kubectl、kustomize、Argo CD、Multipass

k8s 指令

這一頁不是 cheat sheet。每條指令都拆開講：它在 runtime 對哪個元件發了什麼 request、讀的是哪個物件的哪個欄位、在這個專案什麼時候該用。前面幾頁講「CI 怎麼把 image tag 寫進 notes-deploy、Argo CD 怎麼把它套進 k3s」，這一頁是你站在 Mac 前面，想親眼確認那些事真的發生時手上的工具。

  1. CMD-01kubectl 怎麼找到 cluster：kubeconfig 與一次 get podskubectl 不存狀態：每條指令都先讀 kubeconfig 找到 VM:6443，再對 k3s API server 發一次 HTTPS request。
  2. CMD-02看狀態：get 讀物件本身，describe 多拉一份 Eventsget 只讀物件的 status，describe 多查一次 Events。READY 來自 readinessProbe，STATUS 是 reason 不是 phase。
  3. CMD-03Pod 起不來：STATUS 決定下一個指令依 STATUS 分四條路：拉不到 image 看 Events、崩潰看 logs --previous、0/1 看 probe、1/1 查 endpoints。
  4. CMD-04Pod 好好的但網址打不開：由外往內一層一層驗request 經過 /etc/hosts、Traefik、Ingress、Service、Pod 五關，每關有一個指令能單獨驗證。
  5. CMD-05rollout：每個子指令改了哪個欄位，為什麼 undo 會被蓋回去restart 只加一個 annotation；undo 改回舊 image，會被 selfHeal 蓋回。rollback 要在 notes-deploy git revert。
  6. CMD-06kustomize：同一份運算在 CI、manifest-check、Argo CD 各跑一次kustomize build 不碰 cluster：CI 改 newTag、manifest-check 驗算、Argo CD 算同一份再 apply。
  7. CMD-07Argo CD：Application 是一個物件，Sync 與 Health 是兩個獨立判斷Application 是 argocd namespace 裡的物件：Sync 比 Git 與 live，Health 看資源本身，revision 說明讀到哪個 commit。
  8. CMD-08Multipass 與 k3s 主機層：cluster 底下那台 VMkubectl 逾時、IP 變了、AGE 不對時往下查 VM：multipass 管開關與 IP，VM 時鐘會跟 Mac 睡眠一起停。
