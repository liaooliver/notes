k8s 指令

這一頁不是 cheat sheet。每條指令都拆開講：它在 runtime 對哪個元件發了什麼 request、讀的是哪個物件的哪個欄位、在這個專案什麼時候該用。前面幾頁講「CI 怎麼把 image tag 寫進 notes-deploy、Argo CD 怎麼把它套進 k3s」，這一頁是你站在 Mac 前面，想親眼確認那些事真的發生時手上的工具。

CMD-01Mac › ~/.kube/config-k3s → VM:6443 › k3s API server

kubectl 怎麼找到 cluster：kubeconfig 與一次 get pods

kubectl 不存狀態：每條指令都先讀 kubeconfig 找到 VM:6443，再對 k3s API server 發一次 HTTPS request。

kubectl 是一個 HTTP client。每次執行都先讀 kubeconfig（KUBECONFIG 環境變數指的檔案，沒設就讀 ~/.kube/config）。檔案裡有三段：clusters 寫 API server 的 server: 網址與 CA 憑證，users 寫 client 憑證，contexts 把某個 cluster 配上某個 user、外加預設 namespace。current-context 決定這次用哪一組。

這個專案的 API server 是 VM 裡的 k3s，聽 6443。k3s 產生的 /etc/rancher/k3s/k3s.yaml 寫的是 server: https://127.0.0.1:6443，在 VM 裡是對的，搬到 Mac 就錯：Mac 的 127.0.0.1 上沒有 API server。所以 Phase 5.3 先用 sed 換成 VM IP，再存成 ~/.kube/config-k3s。

kubectl -n notes-staging get pods 在 runtime 就是一個 GET /api/v1/namespaces/notes-staging/pods。API server 先驗 client 憑證（k3s.yaml 裡那張憑證屬於 system:masters 群組，等於 cluster-admin），再過 RBAC，最後從 datastore 讀。單節點 k3s 預設的 datastore 不是 etcd，是內嵌的 SQLite，由 kine 模擬 etcd API。

表格欄位是 API server 算好的：kubectl 在 Accept header 要求 Table 格式，server 回傳 NAME / READY / STATUS 等欄位。-o wide 只是多印幾欄，-o yaml 改要完整物件，都還是一次 request。-A 則改打不帶 namespace 的 /api/v1/pods。

kubeconfig
kubectl 唯一的連線設定來源：clusters、users、contexts 三段，加上 current-context。
context
「哪個 cluster + 哪個 user + 預設 namespace」的組合。k3s 產生的三段名稱都叫 default。
6443
k3s API server 的 port。Mac 上的 kubectl 要打的是 <VM IP>:6443。
kine / SQLite
單節點 k3s 預設的 datastore。API server 以為自己在跟 etcd 講話，kine 把它轉成 SQLite 查詢。

CMD-02kubectl › get / describe › Pod · Deployment · ReplicaSet

看狀態：get 讀物件本身，describe 多拉一份 Events

get 只讀物件的 status，describe 多查一次 Events。READY 來自 readinessProbe，STATUS 是 reason 不是 phase。

get 讀的是物件本身。Pod 表格的 READY 是「通過 readinessProbe 的 container 數 / container 總數」，來自 status.containerStatuses[].ready。這個專案每個 Pod 只有一個 container，所以只會是 0/1 或 1/1。STATUS 是 API server 綜合 phase 與 container 的 waiting / terminated reason 算出的一個字，ImagePullBackOff、CrashLoopBackOff 都是 reason，phase 其實是 Pending 或 Running。RESTARTS 是 restartCount，只會往上加。

describe 在 runtime 打兩次 request：先 GET 那個 Pod，再列 events 並用 fieldSelector=involvedObject.name=<pod> 篩出跟它有關的事件。kubelet 拉 image 失敗、probe 失敗、container 被 OOMKilled 都寫在 Events，Pod 物件本身只留最後一個 reason。Events 預設只保留 1 小時，出事要趁早看。

-l component=api 把 label selector 放進 query string，由 API server 篩。web 和 api 共用 app: notes，要分開看就得加 component，這跟 Service selector 用的是同一組字串。-w 在同一條連線加上 watch=true，API server 有變化就推一行下來，拿來盯 rolling update。

READY
通過 readinessProbe 的 container 數 / 總數。0/1 的 Pod 不會出現在 Service 的 endpoints 裡。
STATUS
表格用的摘要。ImagePullBackOff、CrashLoopBackOff 是 container 的 waiting reason，不是 Pod phase。
Events
獨立的物件，kubelet 和 controller 寫進去；describe 最底下那塊就是篩過的 Events，預設留 1 小時。
-l / label selector
在 API server 端篩選。這個專案靠 component=web / component=api 區分兩種 Pod。
-w（watch）
不關閉連線，物件有變化就推送。rolling update 的順序要用它才看得到。

CMD-03kubectl › get pods → describe → logs --previous → endpoints

Pod 起不來：STATUS 決定下一個指令

依 STATUS 分四條路：拉不到 image 看 Events、崩潰看 logs --previous、0/1 看 probe、1/1 查 endpoints。

ImagePullBackOff：kubelet 向 GHCR 要 image 失敗，container 從沒啟動過，logs 一定是空的，原因只在 describe 的 Events。這個專案出現過的原因是 tag 不存在（UC-17：overlay 還沒被 bump，image 字串沒有 tag，等於要 :latest），文件也預先記了 package 是 private 的情況（Phase 6）。

CrashLoopBackOff：image 拉到了，程式啟動後自己結束，kubelet 重啟的間隔越拉越長（10s、20s、40s，上限 5 分鐘）。當下那個 container 可能剛重啟、還沒印東西，要看的是上一個死掉前的輸出：logs --previous。describe 的 Last State: Terminated 會給 exit code。

Running 但 READY 0/1：程式活著，readinessProbe 沒過。notes-api 的 probe 打 /api/health，沒過就不會進 Service 的 endpoints，Traefik 那邊看到的就是 no available server。Events 會有 Readiness probe failed。

Running 1/1 但打不通：Pod 沒問題，問題在更外層。get endpoints 是空的代表 Service selector 對不上；有 IP 就用 port-forward 直接打 Pod，通了就往 Ingress、/etc/hosts 查（cmd-04）。rollout restart 不在這條鏈上：它只重建 Pod，spec 沒變的話結果一樣。

ImagePullBackOff
拉 image 失敗且已進入退避重試。container 沒跑過，logs 是空的。
CrashLoopBackOff
container 反覆啟動又結束，重啟間隔指數拉長，上限 5 分鐘。
logs --previous
讀上一個已結束的 container 的 stdout。RESTARTS 是 0 時會報 not found。
Endpoints
Service 實際接到的 Pod IP:port 清單，只收 READY 的 Pod。k8s 1.33 起建議改看 EndpointSlice。
port-forward
kubectl 經 API server → kubelet 開一條通道直接接到某個 Pod，不經 Service 的分流。

Pod 好好的但網址打不開：由外往內一層一層驗

request 經過 /etc/hosts、Traefik、Ingress、Service、Pod 五關，每關有一個指令能單獨驗證。

瀏覽器打 http://notes-staging.local/api/records，runtime 依序是：Mac 的 /etc/hosts 把網域解析成 VM IP → 連到 VM 的 :80 → Traefik 依 Host header 找到 notes-staging 的 Ingress notes → /api 比 / 長，選 Service notes-api:3000 → Traefik 從這個 Service 的 endpoints 挑一個 Pod IP 直接連過去。

每一關都有一個指令只驗它自己。curl -H 'Host: …' http://<VM IP>/ 跳過 /etc/hosts 直接測 Traefik；get ingress 看 HOSTS；get endpoints 看 Service 接到哪些 Pod；在叢集裡 exec 打 http://notes-api:3000 驗 Service DNS 與 ClusterIP；port-forward 跳過全部直接打 Pod。

症狀 → 第一個要下的指令：

  • 瀏覽器逾時、連不上：multipass info k3s 對 IPv4，再對 /etc/hosts。
  • 純文字 404 page not found（Traefik 的頁）：kubectl -n notes-staging get ingress，HOSTS 跟網址不一致。
  • no available server：kubectl -n notes-staging get endpoints notes-api，多半是空的。
  • 首頁時好時壞、間歇 404：get endpoints notes-web，IP 數量多於 web 的 Pod 數，代表 selector 太寬選到 api。
  • 頁面出來但是舊版：describe pod 看 Image 的 sha，再對 Argo CD 的 revision（cmd-07）。
  • Pod 不是 Running 1/1：回到 cmd-03。

CMD-05kubectl › rollout status / history / restart / undo › Deployment

rollout：每個子指令改了哪個欄位，為什麼 undo 會被蓋回去

restart 只加一個 annotation；undo 改回舊 image，會被 selfHeal 蓋回。rollback 要在 notes-deploy git revert。

Deployment 不直接管 Pod，它管 ReplicaSet。spec.template 只要有任何變動，Deployment controller 就建一個新的 ReplicaSet 並逐步把舊的縮到 0。舊的 ReplicaSet 留著當歷史，它的 deployment.kubernetes.io/revision annotation 就是 rollout history 印的 REVISION。

四個子指令各做一件事。status 只讀：watch Deployment 的 status.updatedReplicas、availableReplicas，全部到位才結束。restart 在 spec.template.metadata.annotations 寫入 kubectl.kubernetes.io/restartedAt，template 變了所以換一批 Pod，image 不變。undo 把上一個 ReplicaSet 的 template 抄回 Deployment，image 變回舊 tag。

這個專案兩個 Application 都開了 selfHeal。Argo CD 比對的是「Git 裡有寫的欄位」：restartedAt Git 裡沒有，不算漂移，restart 會留著；undo 改的是 image，Git 裡有寫，application-controller watch 到變動就判 OutOfSync，自動 apply 回 Git 的 tag。結果是舊 Pod 起來後很快又被換回新版。kubectl edit、set image、scale 都是同一個下場。

正確的 rollback 是在 notes-deploy 上 git revert 那筆 bump commit：desired state 本身變回舊 tag，Argo CD 照著做，而且不會再被蓋回（GitOps 頁）。

ReplicaSet
一版 Pod template 的實體。Deployment 換版就是建新 ReplicaSet、縮舊的。
revision
ReplicaSet 上的序號 annotation，跟 Git commit 沒有對應，預設只留 10 個（revisionHistoryLimit）。
restartedAt
rollout restart 寫進 template 的 annotation。Git 沒有這個欄位，Argo CD 不當它是漂移。
selfHeal
live 與 Git 有差異就自動 apply Git 的版本。這裡兩個 Application 都開著。

kustomize：同一份運算在 CI、manifest-check、Argo CD 各跑一次

kustomize build 不碰 cluster：CI 改 newTag、manifest-check 驗算、Argo CD 算同一份再 apply。

kubectl kustomize overlays/staging 讀 overlay 的 kustomization.yaml，照 resources: ../../base 載入 base 的五份檔案，再套三種變換：namespace: 寫進每個物件的 metadata；images: 用去掉 tag 的完整名稱比對 container 的 image，換成 newName:newTag（所以 notes 不會誤中 notes-api）；patches: 用 JSON Patch 把 Ingress 的 host 換掉。整個過程只讀檔案。

同一個運算在三個地方跑。CI 的 bump job 用 kustomize edit set image，它不渲染，只改 images[].newTag 那一行，然後 commit。notes-deploy 的 manifest-check 對每個 overlay 跑 kubectl kustomize 丟進 /dev/null，只看 exit code。Argo CD 的 repo-server clone notes-deploy 後自己跑一次 build，產出的 YAML 交給 application-controller apply。

kubectl diff -k 是唯一會碰 cluster 的：先在本機 build，再把結果以 server-side dry-run 送給 API server，拿「如果 apply 會變成什麼」跟 live 物件比。selfHeal 開著時它正常應該是空的；不空代表 Argo CD 還沒讀到 Git 最新版，或有人動過 cluster。

kubectl kustomize 只能 build 不能 edit，所以 CI 用的是 runner 內建的獨立 kustomize 執行檔。

Argo CD：Application 是一個物件，Sync 與 Health 是兩個獨立判斷

Application 是 argocd namespace 裡的物件：Sync 比 Git 與 live，Health 看資源本身，revision 說明讀到哪個 commit。

Argo CD 裝在 VM 的 argocd namespace，有自己的 API server（argocd-server）。這個專案不幫它開 Ingress，用 kubectl -n argocd port-forward svc/argocd-server 8443:443：kubectl 在 Mac 聽 8443，每條連線經 k3s API server 與 kubelet 接進 argocd-server Pod。那個 terminal 一關，UI 和 argocd CLI 就都斷了。

兩個 Application 本身是 k8s 物件（kind Application），所以 kubectl -n argocd get applications 不用裝 argocd CLI 也看得到。application-controller 預設每 3 分鐘請 repo-server 對 notes-deploy 的 main 跑 kustomize build，跟 live 物件比，結果寫回 .status。UI 與 argocd app get 都只是在讀這個 .status。

Sync Status 回答「live 跟我讀到的那個 commit 一不一樣」：Synced / OutOfSync。Health Status 回答「資源本身好不好」：Deployment 的新 Pod 還沒 ready 是 Progressing，拉不到 image 會一直 Progressing，超過 progressDeadline 變 Degraded。兩者獨立：Synced + Degraded 代表 Git 的內容被忠實套用了，但那份內容跑不起來。

.status.sync.revision 是它讀到的 commit SHA。Synced 只保證 live 等於這個 SHA，不保證它是 GitHub 上最新的（UC-16）。argocd app diff 印 Git 與 live 的差異，app sync 立即 sync 一次，在 automated 下很少需要。兩個 Application 都是 automated，argocd app rollback 會被拒絕，要退版照樣 git revert。

Multipass 與 k3s 主機層：cluster 底下那台 VM

kubectl 逾時、IP 變了、AGE 不對時往下查 VM：multipass 管開關與 IP，VM 時鐘會跟 Mac 睡眠一起停。

整個 cluster 是 Multipass 開的一台 Ubuntu 24.04 VM，名字就叫 k3s，4 core / 6 GB / 40 GB。multipass list、info 問的是 Mac 上的 multipassd，跟 k8s 無關。VM 停了，kubectl 只會逾時，不會告訴你原因，所以 kubectl 連不上時第一個查的是 VM 的 State。

k3s 在 VM 裡是 systemd service，一個執行檔同時跑 API server、scheduler、controller-manager、kubelet，底下接 containerd。它把 admin kubeconfig 寫在 /etc/rancher/k3s/k3s.yaml，只有 root 能讀，所以 VM 裡要用 sudo k3s kubectl，這個內建的 kubectl 會自動讀那份檔案。Mac 上的 ~/.kube/config-k3s 就是它 sed 過 IP 的副本。

Mac 睡眠時 VM 整台被暫停，時鐘凍結。醒來後 VM 從凍結的時間繼續走，要等 systemd-timesyncd 對時才跳回真實時間。這段空窗裡 k3s 寫下的時間戳（Pod 的 creationTimestamp、Events、Argo CD 的 sync 時間）都是舊的，對時之後 AGE 會憑空多出睡眠時數。

判斷方法是看 VM 的 journal 有沒有一段長時間一行都沒有的空白。有就是睡眠造成的假警報，Git 跟 cluster 其實一致。
