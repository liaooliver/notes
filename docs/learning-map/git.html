第 1 層 · 本機與 GitHub

Git 流程規則

這一層管的是 commit 從你的 Mac 出發，一路到 PR 被 merge 為止：本機 hook 先擋訊息格式，GitHub 再用 branch protection 擋 merge。merge 之後的 push 事件交給 GitHub Actions（CI 頁），這裡只講「什麼時候會叫醒它、什麼時候叫不醒」。

GIT-01GitHub › liaooliver/notes › branches · ci.yml / commitlint.yml 的 on:

分支模型：feature/* → staging → main，每一步叫醒什麼

功能分支 push 什麼都不跑；PR 跑三個 required check；merge 後的 push 才會 build image。只有 push 到 main 會出現人工 Approve 與發版。

這個 repo 有三種分支：從 staging 切出來的 feature/*、集成用的 staging、發布用的 main。每個動作會叫醒哪些 job，完全由 workflow 的 on: 和各 job 的 if: 決定。

runtime 的順序：push feature/* 時，ci.yml 和 commitlint.yml 的 push.branches 只列 main、staging，所以 Actions 一個 run 都不會建立。開 PR 時 pull_request 事件成立，跑 build、white-box、commitlint，這三個就是 branch protection 要的 required check。docker 以後的 job 都寫了 if: github.event_name == 'push'，PR 階段不會出現。

merge 進 staging 產生一次 push：build 和 white-box 重跑一次，接著 docker 推 image、bump-staging 改 staging manifest。merge 進 main 也是 push，但 bump-staging 的 if 要求 refs/heads/staging 而被略過，換成綁 environment: production 的 bump-production 停下來等人按 Approve，再接 release。

為什麼要多一層 staging：發版（Approve、打 tag）是正式動作。如果每個功能分支都直接進 main，每個小改動都要審一次、版號跳得很碎。先在 staging 收斂，merge 頻率和發布頻率就分開了。

required status check
branch protection 指定「這幾個 check 必須 success 才能按 merge」。只在 PR 階段有意義，是第一道 gate。
push 事件
merge 一個 PR 在 GitHub 上等於對 base 分支做一次 push。docker、bump-*、release 只認這個事件。
environment: production
job 綁了有 required reviewer 的 environment，GitHub 會在 job 開始前暫停整個 run，等人 Approve。是只有 main 才有的第二道 gate。
一個改動經過的兩道 gate · 右側程式碼會跟著步驟點亮，點程式碼也能跳到對應步驟

坑

GIT-02本機 › npm install（prepare）› .git/config core.hooksPath › .husky/commit-msg

commit-msg hook：husky 怎麼掛上 git，commitlint 何時執行

npm install 觸發 prepare 跑 husky，husky 把 git 的 hooksPath 指到 .husky/_。之後每次 git commit，git 先跑 commitlint，exit 非 0 就不寫入 commit。

hook 不是 clone 下來就有。package.json 的 prepare script 是 husky，npm 在 npm install / npm ci 結束時會自動執行它。husky 9 不會把檔案複製進 .git/hooks/，而是執行 git config core.hooksPath .husky/_，讓 git 改去 .husky/_/ 找 hook。那個資料夾裡每種 hook 都是兩行的轉接檔，統一交給 .husky/_/h。

當你 git commit 時：git 先把訊息寫進 .git/COMMIT_EDITMSG，再以這個路徑當 $1 執行 .husky/_/commit-msg。h 算出對應的 .husky/commit-msg，把 node_modules/.bin 加進 PATH，用 sh -e 跑它。它只有一行：npx --no -- commitlint --edit $1。commitlint 讀 commitlint.config.js，不合規就 exit 1，git 收到非 0 直接中止，commit 從來沒有存在過。

為什麼放在本機：這是最便宜的一關，錯誤在 commit 當下就出現，不用等 push、等 runner。為什麼 CI 還要再檢一次：git commit --no-verify 會跳過所有 client-side hook，HUSKY=0 也能讓 hook 直接 exit 0。本機 hook 只是加速回饋，真正擋得住的是 PR 上的 Validate Commit Messages（下一個知識點）。

core.hooksPath
git 設定：hook 腳本放在哪個資料夾。預設是 .git/hooks，husky 9 把它改成 .husky/_。
prepare
npm 的生命週期 script，npm install / npm ci 之後自動執行。這個 repo 用它來安裝 husky。
--no-verify
git commit 的參數，跳過 pre-commit 與 commit-msg hook。本機 hook 因此不能當成唯一防線。
npx --no
只用本機已安裝的套件，不自動從 npm 下載。沒跑過 npm install 時這一行會失敗。

實際發生過

這個 sandbox 裡的 clone 還沒跑過 npm install：git config --get core.hooksPath 沒有輸出、.husky/_ 不存在。也就是說，同一個 repo 換一台機器 clone 下來，在 npm install 之前 commit 什麼訊息都不會被擋。

prepare 會在任何 npm install 時執行，包含 Docker build。PR #36 的 commit 記錄了 api image 的坑：npm ci 必須加 --ignore-scripts，否則根目錄 package.json 的 husky prepare 會在 --omit=dev（husky 沒被裝）之後以 exit 127 失敗。

release-automation.md 第二階段：用一個「不知道規範」的子代理故意寫不合格式的訊息，結果連 git commit 都做不出來，本機 hook 就擋下了。

坑
  • 換電腦或重新 clone 後忘了 npm install，hook 就不存在，要到 PR 才會被 CI 抓到。
  • husky 9 用的是 core.hooksPath，去 .git/hooks/ 裡找 commit-msg 是找不到的。
  • GitHub 網頁上按 Squash and merge 時寫的標題不經過任何本機 hook，只有 merge 後的 push 會 lint 它（見 git-03）。
GIT-03GitHub Actions › commitlint.yml › Validate Commit Messages · commitlint.config.js

CI 的 commitlint：PR 檢的跟 merge 後進歷史的，不是同一顆 commit

PR 階段 lint 的是分支上的 commit；squash merge 時在網頁上寫的標題是新 commit，只在 merge 後的 push 才被 lint。它一旦進了受保護分支就改不掉，只能改規則。

commitlint.yml 用 wagoid/commitlint-github-action 在 runner 上跑同一份 commitlint.config.js。fetch-depth: 0 拉完整歷史，這樣 action 才算得出要檢查的 commit 範圍：PR 事件檢 PR 裡的所有 commit，push 事件檢這次 push 帶進來的 commit。

問題出在 squash merge。你在 GitHub 按 Squash and merge 時可以改寫標題與內文，GitHub 用它產生一顆全新的 commit 推進 staging。PR 階段的 check 從來沒看過這顆 commit，第一次 lint 它是 merge 後 push 觸發的那次 run。這次失敗不會擋什麼，因為 commit 已經進去了。

真正的傷害在下一次 promote。staging → main 的 PR 範圍包含這顆 commit，Validate Commit Messages 會紅，而它是 required check，PR 就 merge 不了。staging 受 branch protection 保護、禁止 force push，歷史改不掉，所以唯一的出路是改規則：這個 repo 因此關掉 subject-case、把 body-max-line-length 降成 warning，並把 release 加進 type 清單。

squash merge
把 PR 的所有 commit 壓成一顆新 commit，只有一個 parent。訊息是 merge 當下在網頁上組出來的。
規則等級 0 / 1 / 2
commitlint 的規則嚴重度：0 關閉、1 warning、2 error。只有 error 會讓 exit code 非 0。
subject-case
要求 subject 不能以大寫開頭。中文沒有大小寫，這條只會對開頭的英文專有名詞發作。

GIT-04GitHub › Settings › Branches › main / staging（classic branch protection）

Branch protection：三個 check 名稱、不要求 approve、直接 push 被拒

main 與 staging 都要求走 PR，且三個 check 必須 success。GitHub 用 job 的 name 字串比對 required 清單，不看 workflow 檔名。approve 數設 0，因為單人 repo 自己不能 approve 自己。

main 與 staging 用的是 classic branch protection（Rulesets 頁是空的），兩條分支設定完全相同。規則 A：必須透過 PR，approve 數為 0。規則 B：Build Application、White-box Security Scan、Validate Commit Messages 三個 status check 必須通過。

runtime 時，每個 job 跑完會以它的 name: 當 check run 名稱回報到 PR 的 head commit。GitHub 拿這些字串去比 required 清單，三個都 success 才開放 Merge 按鈕。所以 ci.yml 裡 job 的 id 是 build，但 required check 叫 Build Application。改了 job 的 name，舊名字的 check 就再也不會出現，PR 會一直停在等待狀態。

為什麼不要求 approve：GitHub 不計算 PR 作者自己的 approve。這是單人 repo，要求 1 人 approve 等於所有 PR 都 merge 不了。LLM PR Assist 的三個 job 刻意不列入清單，Gemini 回 429 或 503 時不該擋 merge。

「必須透過 PR」對每個身分都生效，包含 CI 自己的 github-actions[bot]。semantic-release 曾經用 GITHUB_TOKEN 直接 push 版本 commit 到 main，被 GH006 擋下，這個結果直接決定了後來的兩個設計：release 只打 tag 不寫回 repo，manifest 搬到沒有保護的 notes-deploy。

check run
一個 job 回報到某個 commit 上的結果，名稱取 job 的 name。branch protection 以這個名稱比對。
classic branch protection
舊式的分支保護。bypass 名單只能豁免「必須走 PR」，無法針對特定身分豁免 status check。
GH006
classic branch protection 拒絕 push 時的錯誤碼。ruleset 擋下時則是 GH013，可用來判斷是哪種機制。
Include administrators
是否連 repo admin 也受規則限制。這裡是關閉的。

GIT-05GitHub › PR staging → main › Merge 按鈕的選項 · docs/branching-strategy.md

promote staging → main 一定要 merge commit：squash 會切斷祖先

squash 產生的 commit 只有一個 parent（舊 main），git 不知道內容來自 staging。下一次 promote 要重放 22 顆 commit、每個檔案都衝突。修法是 -s ours 把 main 記成 staging 的 parent，而且修的那個 PR 本身也不能 squash。

git 做 merge 時先找 merge-base（兩邊最近的共同祖先），再把 merge-base 之後兩邊各自的變更套在一起。merge commit 有兩個 parent，一個是舊 main、一個是 staging 的 tip，所以下一次 promote 時 merge-base 就是上次的 staging tip，只需要處理新的 commit。

squash 產生的是一顆全新 commit，只有一個 parent：舊的 main。兩邊的檔案內容其實一樣，但 git 在 graph 上找不到這個關係，merge-base 還停在更早的地方。下一次 promote，git 會把 staging 上每一顆已經進過 main 的 commit 再套一次，每個檔案都衝突，而衝突的兩邊看起來還一樣。

修法是在 staging 上做一次 git merge -s ours origin/main：-s ours 策略保留 staging 的檔案內容，只把 main 記成第二個 parent。這顆 merge commit 要進 staging 一樣得走 PR，而那個 PR 也必須用 merge commit；用 squash 又會把第二個 parent 丟掉，等於白做。功能分支進 staging 用 squash 沒問題，因為功能分支之後會被刪掉，不會再從它 merge。

merge-base
兩個分支最近的共同祖先。git merge 只處理 merge-base 之後的變更。
parent
commit 指向上一顆 commit 的連結。merge commit 有兩個，squash commit 只有一個。
-s ours
merge 策略：結果完全採用自己這邊的檔案，但把對方記成 parent。用來「只補祖先關係、不動內容」。

判斷 A 是不是 B 的祖先；exit 0 代表是。用來驗證接回去的方向對不對。

GIT-06GitHub › push / pull_request 事件 › 建立 workflow run 之前 · ci.yml 開頭註解

skip-ci 標記：訊息裡出現那個字串，run 根本不會被建立

GitHub 在建立 run 之前先看 head commit 訊息，任何一行出現 skip-ci 標記就不建立。不是失敗，是不存在：沒有東西能 re-run，PR 上的 required check 也永遠不會出現。

skip-ci 標記（方括號包住 skip 與 ci）原本是給 bot 用的：CI 自己 push 的 commit 帶上它，就不會再觸發 CI，避免無限迴圈。GitHub 處理 push 與 pull_request 事件時，會在建立 workflow run 之前檢查 head commit 的訊息，找到這個字串就整個略過，Actions 頁面上什麼都不會出現。

squash merge 讓它很難防。squash 的預設內文是把 PR 裡每顆 commit 的訊息串起來，只要其中一顆為了講解舊設計而寫出這個字串，整顆 squash commit 就帶著它。push 到 main 時 ci.yml 和 commitlint.yml 都不會建立 run：沒有 image、沒有 Approve、沒有發版，promote 的 release: 標題也沒被 lint。

workflow_dispatch 是事後補加的逃生門，但它有前提：GitHub 只認預設分支上那份 workflow 檔有沒有這個觸發。修正 PR 只能進 staging，要等下一次 promote 才會到 main，所以當下用不了。放在 PR 分支的 commit 上更麻煩：三個 required check 都不會出現，而手動觸發的 run 不會回填成 PR 的 check，唯一解法是 amend 訊息再 force push。

workflow_dispatch
讓 workflow 可以從 Actions 頁面或 API 手動觸發。只有預設分支上的 workflow 檔有這個觸發時才能用。
head commit
push 或 PR 最新的那顆 commit。GitHub 只看它的訊息決定要不要略過。
no checks reported
gh pr checks 在一個 check 都沒有時的回覆。不是失敗訊息，最容易被誤判成還在排隊。

GIT-07本機 commit 訊息 › main 的歷史 › release job › @semantic-release/commit-analyzer

Conventional Commits 的 type 決定下一個版號

發版時 commit-analyzer 逐顆讀 main 上次 tag 之後的 commit header：feat 升 minor，fix / perf 升 patch，BREAKING CHANGE 升 major，其餘不發版。取所有 commit 中最高的那一級。

commit 訊息的 type 不只是格式要求，它是版號的輸入。release job 只在 push main 時跑，semantic-release 先找最近的 notes-v* tag，列出之後進入 main 的所有 commit，再交給 commit-analyzer 用預設規則逐顆判斷。

判斷只看 header（第一行）：feat 是 minor，fix、perf 與 revert 是 patch，footer 有 BREAKING CHANGE 是 major。docs、chore、ci、release 都不在規則裡。GitHub 產生的 merge commit，header 是 Merge pull request #N ...，解析不出 type，也不會發版。最後取所有 commit 裡最高的一級。

所以真正決定版號的，是功能分支進 staging 時留在歷史上的那幾顆 commit。用 squash 時，就是你在網頁上寫的那個標題。promote PR 標題寫 release: 只是為了通過 commitlint，它本身不會讓版號變動。整個 promote 如果只有 docs / chore，就不會打 tag。細節（tag 格式、只打 tag 不寫回 repo）放在 CI 頁的 release。

commit-analyzer

header
commit 訊息第一行，格式 type(scope): subject。版號只看這一行與 footer。
BREAKING CHANGE
寫在 commit footer 的標記，不論 type 都會升 major。
