第 4 層 · Multipass VM 裡的 k3s

k8s runtime

這一層從「manifest 已經被 Argo CD apply 進 cluster」開始。接下來是 k3s 自己的事：controller 把 Deployment 變成 Pod、Service 靠 label 找到 Pod、Traefik 把瀏覽器的 request 送到對的容器。每個知識點都拆成「誰呼叫誰、依序發生什麼」。

K8S-01Mac › Multipass VM k3s › k3s（kube-system / argocd / notes-*）

環境全貌：Mac 裡的 VM 裡的單節點 k3s

整個 cluster 是 Mac 上一台 6 GB 的 arm64 VM；control-plane 與 worker 是同一台，Traefik、ServiceLB、CoreDNS 都是 k3s 內建。

Mac 上用 Multipass 開一台 Ubuntu VM，名稱就叫 k3s，4 core、6 GB、40 GB 磁碟。Apple Silicon 上的 VM 是 linux/arm64，這決定了後面所有 image 都得是 multi-arch。

VM 裡跑的是 k3s 單節點。API server、scheduler、controller-manager、kubelet、containerd 全在同一個行程群裡，節點角色顯示 control-plane,master，但一般 Pod 也照樣排上來。k3s 安裝時順便帶了 Traefik（Ingress controller）、ServiceLB（又叫 klipper-lb）、CoreDNS、local-path storage，所以 Ingress 不用另外裝。

記憶體是這台機器的真正限制。Argo CD 一套約 1.5 GB，是 VM 裡最大的一塊；兩個 namespace 的應用加起來不到 100 MB。不做多節點的理由寫在 roadmap 第 0.2 節：多節點練的是 affinity、taint、drain 這類排程技能，不在這個專案的學習範圍。

Mac 上的 kubectl 透過 ~/.kube/config-k3s 連 VM 的 6443 port。從 VM 撈出來的 kubeconfig 寫的是 127.0.0.1，不換成 VM 的 IP，kubectl 會去連 Mac 自己然後逾時。

k3s
精簡版 Kubernetes，單一 binary。這裡是單節點，control-plane 與 worker 是同一台 VM。
containerd
kubelet 透過 CRI 呼叫的容器 runtime，負責拉 image、建容器。k3s 內建，不需要 Docker。
ServiceLB
k3s 內建的 LoadBalancer 實作。替 type: LoadBalancer 的 Service 在節點上開 hostPort，Traefik 的 80/443 就是這樣佔住 VM 的 port。
kube-system
k3s 內建元件所在的 namespace：traefik、svclb-traefik、coredns、metrics-server。

實際發生過

Mac 睡醒後的假警報（liaooliver/notes#43）。production 的 Pod 跑著 sha-1044bc45，AGE 顯示 18h，但 notes-deploy 裡把 image 換成這個 tag 的 commit efd8792 是 2026-09-26 12:01:40 UTC 才推的，看起來像有人繞過 Git 直接改了 cluster。

實際原因是 Mac 睡眠時 VM 被一起暫停，VM 時鐘停住，醒來後 systemd-timesyncd 才把它往前跳。journalctl 裡有一段 2026-09-25T17:57:36Z → 2026-09-26T12:04:09Z 完全沒有紀錄的斷點。同一個 cluster 裡，對時之後才建的 staging Pod AGE 是正常的幾分鐘。

另外 5.2 節原本憑印象寫 v1.31.x+k3s1，liaooliver/notes#42 改成實機的 v1.36.4+k3s1。

坑
  • kubeconfig 的 server: 是 127.0.0.1，直接用會連到 Mac 自己的 6443 然後逾時。
  • VM 重開後 IP 可能會變，/etc/hosts 和 ~/.kube/config-k3s 兩邊都要更新。
  • Mac 睡醒後 VM 裡的時間戳不可信：Pod 的 AGE 會多出睡眠時數，先看 journal 有沒有斷點再下結論。
  • 舊版 Multipass 的參數是 --mem 不是 --memory。
K8S-02k3s › namespace notes-staging / notes-production

Namespace：一個 cluster 放兩個環境

物件的唯一鍵是 kind + namespace + name，所以兩個 notes-web 不衝突；namespace 隔開的是名稱，不是網路也不是資源。

base 的五份 manifest 都沒寫 namespace。overlay 只加一行 namespace: notes-staging，kustomize build 時把它寫進每個物件的 metadata.namespace。Argo CD 再把結果 apply 進去，Application 的 CreateNamespace=true 讓 namespace 不存在時先建出來。

API server 存物件時用的鍵是 kind + namespace + name。所以 Deployment/notes-staging/notes-web 和 Deployment/notes-production/notes-web 是兩筆不同的資料，controller 各自管各自的 Pod。Service 的短名稱也是 namespace 範圍：staging 的 Pod 查 notes-api，CoreDNS 回的是 staging 那個 Service。

namespace 沒有隔開的東西：同一台 Node 的 CPU 與記憶體、Pod 之間的網路（沒有 NetworkPolicy 時，任一 Pod 都連得到另一個 namespace 的 Pod IP）、以及 cluster 層級的物件。Traefik 只有一個，它讀所有 namespace 的 Ingress，兩個環境能分開完全靠 Ingress 的 host 不同。

選單 cluster 兩 namespace 而不是兩個 cluster，是因為第二套 k3s 要多一台 VM、多一份 kubeconfig 和跨 VM 網路，記憶體也不夠（roadmap 第 0.5 節）。

namespace
物件名稱的範圍。同一個 namespace 內 name 不能重複，跨 namespace 可以。
cluster-scoped
不屬於任何 namespace 的物件，例如 Node、Namespace、IngressClass。兩個環境共用。
CreateNamespace=true
Argo CD 的 syncOption：目標 namespace 不存在就先建。

K8S-03k3s › kube-controller-manager › Deployment / ReplicaSet controller

Deployment → ReplicaSet → Pod：image tag 變了之後

tag 一變就產生新的 ReplicaSet；replicas 1 的預設策略是先多開一個新 Pod，readinessProbe 通過之後才殺舊 Pod。

Argo CD apply 的只是一個欄位的變化：spec.template.spec.containers[0].image 從 sha-舊 變成 sha-新。Deployment controller 對 template 算一個 hash，找不到同 hash 的 ReplicaSet，就建一個新的。舊的 ReplicaSet 不刪，縮成 0 留著，預設保留 10 份。

manifest 沒寫 strategy，所以用預設的 RollingUpdate：maxSurge 25%、maxUnavailable 25%。replicas 是 1 時，surge 進位成 1、unavailable 捨去成 0，意思是「可以多一個，但一個都不能少」。所以一定是先開新 Pod，新 Pod Ready 之後才縮舊的。

「Ready」由 readinessProbe 決定。web 打 GET / :80，api 打 GET /api/health :3000，預設每 10 秒一次，回 200–399 算通過。通過前，新 Pod 的 IP 不會進 Service 的 endpoints，流量全在舊 Pod 上。

沒有 readinessProbe 會怎樣：容器一啟動就算 Ready，舊 Pod 立刻被殺，nginx 或 Express 還沒開始 listen 的那幾秒，request 會拿到 502。反過來 probe 一直失敗時，舊 Pod 不會被動，流量照舊，600 秒後 Deployment 標 ProgressDeadlineExceeded。

ReplicaSet
負責「維持 N 個長這樣的 Pod」。每個不同的 Pod template 對應一個 ReplicaSet，名稱後綴就是 template hash。
maxSurge / maxUnavailable
rolling update 時最多多開幾個、最多少幾個。預設都是 25%，replicas 1 時換算成 1 與 0。
readinessProbe
kubelet 定期打的健康檢查。通過才標 Ready，Ready 的 Pod 才會進 endpoints 接流量。
terminationGracePeriodSeconds
舊 Pod 收到 SIGTERM 後最多等幾秒才 SIGKILL，預設 30。

實際發生過

docs/use-cases.md UC-15 第 6 步記錄的就是這一段：「新 pod 通過 readinessProbe 之後才殺舊 pod」，全程沒有人敲 kubectl。

坑
  • 沒有 readinessProbe，rolling update 會在新 Pod 還不能服務時就砍舊 Pod，Argo CD 顯示 Healthy，但實際有幾秒 502。
  • readinessProbe 只控制「接不接流量」，不會重啟容器；要自動重啟卡死的行程是 livenessProbe，這個專案沒設。
  • rolling update 期間短暫有 2 個 Pod，requests 也短暫加倍，記憶體預算要留這個餘裕。
K8S-04k3s › Service / Endpoints / CoreDNS › notes-staging

Service 與 label selector：流量怎麼找到 Pod

Service 用 selector 挑 Pod，endpoints controller 把「符合 label 且 Ready」的 Pod IP 列成清單；少一個 label 就會選錯 Pod，而且不會報錯。

web 和 api 的 Pod 都帶 app: notes，差別只在 component: web 或 component: api。Service notes-web 的 selector 兩個都要求，所以只選得到 web 的 Pod。endpoints controller 持續 watch Pod，把「label 符合而且 Ready」的 Pod IP 加上 targetPort 寫進同名的 Endpoints 物件。

Service 本身拿到一個 ClusterIP（k3s 預設從 10.43.0.0/16 配），這是虛擬 IP，沒有任何網卡擁有它。kube-proxy 在節點上寫 iptables 規則，把送往 ClusterIP:port 的封包轉到 Endpoints 裡的某個 Pod IP。CoreDNS 負責名稱：notes-api.notes-staging.svc.cluster.local 解析成那個 ClusterIP；同 namespace 內寫 notes-api 就夠。

如果 notes-web 的 selector 少了 component，api 的 Pod 也會進它的 Endpoints。targetPort 是數字 80，被分到 api Pod 的 request 會打到 api Pod 的 80 port，那裡沒有行程在聽，連線被拒。結果是大約一半的首頁 request 失敗。docs 裡寫的症狀是「首頁有時正常有時 404」；依這份 manifest 推算，比較可能是 Traefik 回 502，共同點是間歇性、而且 kubectl get pods 全部 Running。

Deployment、Service、Ingress 三層之間沒有任何自動關聯，全靠字串對上。kubectl get endpoints 是唯一能直接看出「Service 後面到底接到誰」的地方。

selector
Service 用來挑 Pod 的 label 條件，所有 key=value 都要符合才算。
Endpoints / EndpointSlice
Service 目前接到的 Pod IP:port 清單，只收 Ready 的 Pod。k8s 1.33 起建議改看 EndpointSlice。
ClusterIP
Service 的虛擬 IP，只在 cluster 內有效，由 kube-proxy 的 iptables 規則轉成 Pod IP。
CoreDNS
cluster 內的 DNS。把「服務名.namespace.svc.cluster.local」解析成 ClusterIP。

K8S-05Mac 瀏覽器 › /etc/hosts › VM :80 › Traefik › Ingress › Pod

一個 request 的完整路徑：瀏覽器到 Pod

/etc/hosts 把網址指到 VM，ServiceLB 把 80 port 交給 Traefik，Traefik 依 host 與最長前綴挑 Service，再直接連 Pod IP。

notes.local 不存在於任何 DNS。Mac 的 /etc/hosts 手動寫一行 192.168.64.5 notes.local notes-staging.local，瀏覽器解析完就對 VM 的 80 port 開 TCP 連線，Host header 帶著原本的網址。

VM 的 80 port 是 ServiceLB 開的 hostPort，它把封包轉給 kube-system 裡的 Traefik。Traefik 手上有所有 namespace 的 Ingress 規則，先比 host：notes.local 對到 notes-production 的 Ingress，notes-staging.local 對到 notes-staging 的。host 都對不到就回 Traefik 自己的 404 page not found。

接著比路徑。/api/records 同時符合 /api 與 /，Traefik 用最長前綴，所以 /api 勝出，交給 notes-api:3000；其他路徑都落到 notes-web:80。Traefik 不走 ClusterIP，它直接讀 Service 的 endpoints，連 Pod IP。

這樣設計讓前後端在瀏覽器眼中是同一個 origin。前端只寫 fetch('/api/records')，不用處理 CORS，也不用注入 API 位址。本機開發時 vite.config.js 的 proxy 做同樣的事。

/etc/hosts
Mac 本機的名稱對照表，優先於 DNS。notes.local 能用全靠這一行。
Ingress
描述「哪個 host + 路徑送給哪個 Service」的規則。本身不處理流量，由 Traefik 讀取並執行。
pathType: Prefix
以路徑段為單位的前綴比對。多條都符合時，Traefik 選最長的那條。
Host header
HTTP request 帶的原始網址名稱。IP 相同時，Traefik 只能靠它分辨是哪個環境。

K8S-07k3s › kubelet › containerd › ghcr.io

image pull：kubelet 怎麼從 GHCR 拿到 arm64 那一份

public package 用匿名 token 就拉得到，不需要 imagePullSecrets；tag 背後是 image index，containerd 自己挑 linux/arm64。tag 不存在時 restart 沒有用。

Pod 排到 node 之後，kubelet 請 containerd 拉 image。tag 是 sha-… 時 imagePullPolicy 預設 IfNotPresent，本機有就不拉。containerd 先向 ghcr.io/token 要一個匿名的 pull token，再拿 tag 去要 manifest。liaooliver/notes 是 public repo，GHCR package 也是 public，匿名 token 就夠，所以兩份 Deployment 的 imagePullSecrets 都維持註解。

CI 用 buildx 同時出 amd64 與 arm64，GHCR 上的 tag 指向一份 image index，裡面掛兩個 digest。containerd 知道自己在 linux/arm64 上，只下載那個 digest 的 layer。manifest 裡永遠只寫 tag，不寫架構。如果 image 只有 amd64，錯誤會是 no matching manifest for linux/arm64/v8，完全不提示是 CI 那邊少了一行 platforms。

拉失敗時 Pod 先是 ErrImagePull，重試間隔逐次拉長後變成 ImagePullBackOff。Phase 9 那天的原因是 image 沒有 tag：沒寫 tag 等於 :latest，GHCR 上沒有這個 tag。kubectl rollout restart 只在 template 加一個 restartedAt annotation，image 欄位沒變，新 Pod 拉的還是同一個不存在的東西。要改的是 manifest 裡的 tag，也就是讓 Argo CD 讀到後面那筆 bump commit。

image index
又叫 manifest list。一個 tag 底下掛多個平台各自的 image digest。
ImagePullBackOff
拉 image 失敗，kubelet 已經進入拉長間隔重試的狀態。多半是 image 或 tag 不存在、或沒有權限。
imagePullSecrets
Pod 拉 private image 時用的帳密。public package 不需要。
imagePullPolicy
何時重新拉 image。有明確 tag 時預設 IfNotPresent，沒 tag 或 :latest 時預設 Always。

  • GHCR 上 notes 與 notes-api 是兩個獨立 package，可見性各自設定；notes-api 第一次 push 後要手動改成 public。
  • 只有 api 卡 ImagePullBackOff 時，症狀是「畫面正常、打 API 才壞」，很容易先去翻 Express 程式碼。
  • 改成 private 時要先建 ghcr-pull secret 再取消註解，而且 web 與 api 兩份 Deployment 都要改。
  • rollout restart 只換 annotation，不換 image；image 不存在的問題它解決不了。
K8S-08notes-deploy › base/*-deployment.yaml › resources

resources：requests 給 scheduler 看，limits 給 kernel 執行

scheduler 只拿 requests 算放不放得下；limits 寫進 cgroup，CPU 超過會被限速，記憶體超過會被 OOMKilled。

requests 是排程用的預約量。scheduler 把 Node 上所有 Pod 的 requests 加總，新 Pod 的 requests 放得進剩餘的 allocatable 才排上去，跟 Pod 實際用多少無關。CPU requests 另外換算成 cgroup 的權重，CPU 滿載時按比例分。

limits 由 kubelet 交給 containerd 寫進容器的 cgroup。CPU 超過 limit 會被 CFS quota 限速，行程變慢但不會死。記憶體超過 limit，kernel 的 OOM killer 直接殺掉容器裡的行程，狀態顯示 OOMKilled、exit code 137，kubelet 依 restartPolicy 重啟容器，反覆發生就變成 CrashLoopBackOff。

這個專案的值很小：web 預約 10m CPU / 16Mi，上限 100m / 64Mi；api 預約 10m / 32Mi，上限 200m / 128Mi。兩個 namespace 加起來 requests 只有 96Mi，limits 上限 384Mi，在 6 GB 的 VM 裡幾乎沒有存在感。requests 小於 limits，所以 QoS class 是 Burstable。

api 的 limit 跟記憶體資料放在一起看才有意義：records 陣列只增不減，理論上一直 POST 到超過 128Mi，容器會被 OOMKilled，重啟後資料全部歸零。

requests
scheduler 用來判斷 Pod 能不能排上某個 Node 的預約量。
limits
寫進 cgroup 的硬上限。CPU 超過被限速，記憶體超過被殺。
OOMKilled
容器因記憶體超過 limit 被 kernel 殺掉的終止原因，exit code 137。
QoS class
依 requests/limits 分成 Guaranteed、Burstable、BestEffort；Node 記憶體不足時 BestEffort 最先被驅逐。

K8S-09k3s › Traefik › Ingress /api › Service notes-api › endpoints

Traefik 回 no available server：從外往內排錯

no available server 代表路由有對到，但那個 Service 的 endpoints 是空的：不是 selector 對不到 Pod，就是 Pod 還沒 Ready。

Traefik 的 Kubernetes Ingress provider 持續 watch 每個被 Ingress 引用的 Service 的 endpoints，拿裡面的 Pod IP 當作 server 清單。request 進來、host 與路徑都對上了，清單卻是空的，Traefik 就回 HTTP 503，內文是 no available server。

endpoints 為空只有兩種原因。第一是 selector 對不到任何 Pod：label 拼錯、少一個、或 Pod 根本不存在。第二是 Pod 存在但不 Ready：readinessProbe 沒過，或容器根本沒起來（例如卡在 ImagePullBackOff）。這時 kubectl get service 看起來正常，kubectl get pods 可能還是 Running，只有 endpoints 誠實地是空的。

排錯順序由外往內。瀏覽器逾時看 /etc/hosts；Traefik 的 404 page not found 看 Ingress 的 host；no available server 或 502 看 endpoints；頁面出來但內容不對，看 Pod 的 image tag。修正一律改 notes-deploy 的 manifest，讓 Argo CD sync；直接 kubectl edit 會被 selfHeal 改回去。

no available server
Traefik 在「路由有對到、但後端沒有任何可用 server」時回的 503 內文。
404 page not found
Traefik 在「host/路徑對不到任何路由」時回的白底頁，跟 nginx 的 404 不同。
selfHeal
Argo CD 發現 cluster 被手動改動時，自動改回 Git 的版本。

實際發生過

docs/gitops-roadmap.md Phase 9 開頭寫明：從單服務變雙服務有五個地方要同時改，漏一個就會出現「/ 正常但 /api 回 no available server」。

Phase 9 上線那天（notes-deploy 4b60f81 到 377d045 之間約 20 分鐘），notes-api 的 Pod 卡在 ImagePullBackOff，從未 Ready，endpoints 必然是空的。依機制推算，那段時間打 /api 走的就是這張圖；當時 Traefik 的實際回應沒有留下紀錄。

坑
  • kubectl get service 永遠有 ClusterIP，看不出後面有沒有 Pod；一定要看 endpoints。
  • 直接 kubectl edit Service 修 selector，Argo CD 的 selfHeal 會把它改回 Git 的錯誤版本；要改 notes-deploy。
  • selector 太寬時不會出現 no available server，而是間歇性失敗；endpoints 的 IP 數量比 Pod 數多就是這個情況。
